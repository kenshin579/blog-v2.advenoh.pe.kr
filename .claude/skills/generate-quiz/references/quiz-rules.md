# 퀴즈 작성 규칙

글에 인터랙티브 퀴즈를 넣으려면 본문에 ` ```quiz ` 코드펜스를 열고 YAML로 문항을 적는다. 클라이언트에서 퀴즈 UI로 렌더되며, 보기를 고르면 즉시 판정·해설이 나오고 세트 단위로 점수가 집계된다. 표본: `contents/go/golang-generics-1-개요와-기본-문법/index.md`의 6장(`npm run check:quiz`를 에러·경고 0으로 통과한다).

## 1. 유형과 필드

유형은 4가지다.

- `mcq`: 객관식. `choices`(문자열 배열) + `answer`(0부터 세는 정답 인덱스)
- `ox`: OX. `answer`는 `true`/`false`
- `code`: `lang` + `code`(블록 스칼라) 코드 블록이 붙는 객관식. 필드는 `mcq`와 동일하게 `choices` + `answer`
- `blank`: 빈칸 채우기. `q`에 빈칸 `___`(밑줄 3개)을 넣고, `answer`는 허용 답 문자열 배열 (비교 규칙은 4절)

전 유형 공통으로 `q`(문제)와 `explain`(해설)이 필수다.

**`answer`는 0부터지만 화면에는 1부터 번호가 붙는다.** `mcq`·`code`의 보기는 `1.`~`4.`로 렌더되므로 `answer: 0`이 화면의 `1.`이다. 해설에서 보기를 가리킬 때는 화면 번호(1부터)를 쓴다. `ox`는 O/X라 번호가 붙지 않는다.

**최소 예시 (4유형 각 1문항):**

````markdown
```quiz
- type: mcq
  q: "질문 문장이다"
  choices: ["첫째 보기", "둘째 보기", "셋째 보기", "넷째 보기"]
  answer: 1
  explain: "둘째가 맞다. (2.1)"

- type: ox
  q: "참인지 거짓인지 묻는 문장이다"
  answer: false
  explain: "거짓이다. (2.2)"

- type: code
  q: "이 코드는 무엇을 출력하나?"
  lang: go
  code: |
    x := 2 + 3
    fmt.Println(x)
  choices: ["5를 출력한다", "23을 출력한다", "0을 출력한다", "컴파일 에러"]
  answer: 0
  explain: "덧셈 결과다. (2.3)"

- type: blank
  q: "빈칸에 들어갈 말은 ___ 이다."
  answer: ["고루틴", "goroutine"]
  explain: "고루틴이다. (2.4)"
```
````

`answer`의 형태가 유형마다 다르다: mcq·code는 인덱스(숫자), ox는 불리언(`true`/`false`), blank는 허용 답 문자열 배열이다.

## 2. 형식 규칙

- `explain`은 전 유형 필수. 관련 절 안내("(2.2절)")를 포함한다
- 문자열은 큰따옴표, `choices`는 인라인 배열, `code`는 블록 스칼라(`|`)
- 세트당 10문항 권장, 4유형을 섞는다
- 영문판(`index_en.md`)에도 같은 문항 수·유형·정답 인덱스로 작성한다

## 3. 품질 규칙 (리뷰에서 확립됨)

- **정답 위치를 고르게 분산한다.** 정답이 한 인덱스에 쏠리면 같은 버튼만 눌러 만점이 나온다. 유형 안에서도 쏠리지 않게 본다
- **같은 문항의 보기 길이를 비슷하게 맞춘다.** 정답만 설명형으로 길면 길이만으로 정답이 티 난다
- mcq는 4지선다로 통일하고, 오답은 본문을 대충 읽으면 고를 만한 혼동으로 만든다. 단, 본문 어딘가에서 참인 서술을 오답으로 배치하지 않는다
- **본문에 근거가 있는 것만 묻는다.** 일반적으로 맞는 사실이어도 그 글에 없으면 쓰지 않는다
- 유형 순서를 기계적으로 반복하지 않는다 (`mcq→code→ox→blank` 사이클 같은 것)
- 블록을 글 중간에 여러 개 둘 수 있고 세트마다 점수가 따로 난다
- **YAML이 깨지면 그 블록은 코드 블록으로 노출된다.** 개별 문항이 형식에 안 맞으면 그 문항만 조용히 빠진다(6절 E1/E2). 저장 전 파싱 확인이 필수인 이유다

## 4. 정답 노출 (가장 자주 나오는 결함)

퀴즈 UI는 한 세트의 **전 문항을 한 화면에 동시에** 렌더한다(`components/article/quiz.tsx`가 `questions.map`으로 전부 그린다). 작성자는 문항을 하나씩 쓰기 때문에 이 결함은 눈으로 잘 안 잡힌다. 실제로 5편 작업에서 4편에 나왔다.

- **blank 정답 문자열이 다른 문항의 `q`·`choices`·`code`에 등장하면 안 된다.** `explain`은 그 문항을 푼 뒤에만 보이므로, 앞 문항의 `explain`이 뒤 문항 답을 흘리는 경우만 문제다
- 흔한 토큰(`any`, `struct`, `<-chan`, `after` 등)은 blank 정답으로 부적합하다. 본문·코드 곳곳에 자연스럽게 등장한다
- 문자열 검사만으로는 부족하다. 예를 들어 `대괄호`가 정답일 때 grep은 0건이어도 code 스니펫의 `[T any]`가 답을 보여준다
- 영문판은 정답이 흔한 영어 단어와 겹치는지 따로 본다. 비교가 대소문자 무시라, 지문의 전치사 `after`가 허용 답 `After`와 매칭된 사례가 있다

**실제로 검출된 사례 두 건:**

> `contents/cloud/grafana-완벽-가이드-1-.../`의 9번 빈칸 정답이 `"prometheus"`였다. 글의 주제어라 자기 지문과 1번·10번 문항에 자연스럽게 등장했다.
>
> `contents/go/go-fx-의존성-주입/`의 7번 빈칸 정답이 `["name", "name:"]`이었는데 8번 OX 지문이 "`group:` 태그로만 가능하고, `name:` 태그로는 아예 불가능하다"였다. 영문판은 3번 보기 "Alphabetically by constructor name"과도 겹쳤다.

**비교 규칙의 정정:** blank 비교는 "공백·대소문자 무시"가 아니라, 실제 `lib/quiz.ts`의 `normalizeBlankAnswer`(`trim()` + `toLowerCase()`) 기준으로 **앞뒤 공백과 대소문자만** 무시한다. 안쪽 공백은 구분되므로 띄어쓰기 변형은 허용 답에 함께 적는다. 예: `["2KB", "~2KB", "2 KB"]`, `["1.18", "go1.18", "go 1.18"]`.

오답일 때 화면에 보여주는 정답은 배열의 첫 원소다(`components/article/quiz.tsx`의 `question.answer[0]`). 표준형을 앞에 둔다.

## 5. 배치 규칙

글당 quiz 블록 1개. 렌더러는 여러 개를 지원하고 세트마다 점수가 따로 나지만, 관례는 1개다.
위치는 본문 마지막 장 다음, 마무리·정리·FAQ·참고 앞이다. 독립 H1 장으로 만들고 제목은 `# N. 퀴즈`로 한다.
도입 문장을 한 줄 붙인다. 예: "여기까지 읽었으면 풀 수 있는 문제들이다. 답을 고르면 바로 해설이 나온다."
퀴즈가 있는 기존 8편이 예외 없이 이 형태다.

## 6. 작성 후 확인

`npm run check:quiz -- {category}/{slug}`로 검사한다(인자 없으면 `contents/` 전체 스캔).

**에러 (종료 코드 1):**

| 코드 | 내용 |
|------|------|
| E1 | YAML 파싱 실패 또는 최상위가 배열 아님 |
| E2 | 형식에 안 맞아 조용히 빠지는 문항 |
| E3 | blank에 빈칸 `___` 없음 |
| E4 | blank 정답이 다른 문항 지문에 노출 |
| E5 | blank 정답이 자기 지문에 노출 |
| E6 | 한·영 구조 불일치 |
| E7 | 닫는 quiz 펜스 빠짐 |
| E8 | 지목한 대상에 quiz 블록 없음 |
| E9 | blank 정답이 비어 있음 |

**경고 (종료 코드 0, 사람이 판단):**

| 코드 | 내용 |
|------|------|
| W1 | 정답 인덱스 쏠림. **mcq와 code를 합쳐서 보고 한 값이 절반을 넘으면 발화한다. 유형별(mcq만, code만) 쏠림은 검사하지 않으므로 사람이 본다** |
| W2 | 정답 보기만 유독 김 |
| W3 | mcq가 4지선다 아님 |
| W4 | `explain`에 절 참조 없음 |
| W5 | 문항 수가 10이 아님 |

**스크립트가 못 잡는 것:**

> `code` 스니펫이 실제로 컴파일되는지. Go는 미사용 변수가 컴파일 에러다. 의도적으로 에러를 묻는 문항이면 그 에러만 나야 한다.
>
> 퀴즈 절을 넣어 뒤 섹션 번호를 밀었을 때 본문에 그 번호를 가리키는 참조가 남아 있는지. 한국어판과 영문판의 섹션 번호가 다를 수 있으니 파일별로 본다.
>
> 의미상 정답 노출. E4·E5는 문자열 포함만 본다. 4절의 `대괄호` ↔ `[T any]` 같은, 의미는 같지만 문자열이 다른 노출은 원리적으로 못 잡는다.
>
> 유형별 정답 인덱스 쏠림. W1은 mcq+code 합산만 본다(3절). mcq만, code만 쏠렸는지는 사람이 세어봐야 한다.
