12편까지 WebRTC의 개념, 구현, 운영을 모두 다루었다. 이번 **마지막 편**에서는 한 걸음 물러서서 **WebRTC를 언제 쓰면 안 되는가**를 생각해본다. 모든 기술에는 적합한 영역이 있다. WebRTC가 최선이 아닌 상황을 알고, 대안 기술을 이해하는 것이 올바른 기술 선택의 출발점이다.

# 1. WebRTC가 과한 경우

## 1.1 WebRTC의 본질

WebRTC는 **브라우저 간 P2P 실시간 통신**을 위해 설계되었다. 핵심 강점은 다음과 같다.

- 초저지연 (< 300ms)
- 양방향 미디어/데이터 통신
- NAT/방화벽 자동 우회
- 의무적 암호화 (DTLS + SRTP)

하지만 이 강점에는 대가가 따른다.

```
[WebRTC 도입 비용]

  ┌─────────────────────────────────────────────────┐
  │  인프라 비용                                     │
  │  ├── Signaling 서버 (WebSocket 기반, 직접 구현)  │
  │  ├── STUN 서버 (경량, 저비용)                    │
  │  ├── TURN 서버 (고비용 - 모든 트래픽 릴레이)     │
  │  └── SFU/MCU 서버 (다자간 통화 시)               │
  ├─────────────────────────────────────────────────┤
  │  개발 복잡도                                     │
  │  ├── SDP Offer/Answer 상태 머신                  │
  │  ├── ICE 후보 수집/교환/연결                     │
  │  ├── 코덱 협상, 미디어 파이프라인                 │
  │  └── 네트워크 환경별 대응 (NAT, 방화벽)          │
  ├─────────────────────────────────────────────────┤
  │  운영 부담                                       │
  │  ├── TURN 서버 대역폭 비용                       │
  │  ├── 접속자당 리소스 선형 증가                    │
  │  └── 디버깅 난이도 (UDP, P2P, ICE 상태)          │
  └─────────────────────────────────────────────────┘
```

## 1.2 WebRTC가 과한 5가지 시나리오

### 1.2.1 대규모 단방향 스트리밍

1만 명 이상에게 라이브 영상을 송출하는 경우다. WebRTC는 **시청자마다 개별 연결**을 유지해야 하므로 비용이 시청자 수에 비례하여 선형 증가한다. 반면 HLS/DASH는 CDN 캐싱으로 수백만 시청자를 저비용으로 커버한다.

```
[비용 비교: 10,000명 시청자, 1시간, 720p]

  WebRTC (SFU)                    HLS (CDN)
  ┌──────────────────┐            ┌──────────────────┐
  │ SFU 서버 10대     │            │ Origin 서버 1대   │
  │ 각 1,000명 처리   │            │ CDN 엣지 자동분산 │
  │                  │            │                  │
  │ 비용: ~$900      │            │ 비용: ~$60       │
  │ (서버+대역폭)     │            │ (CDN 전송비용)    │
  └──────────────────┘            └──────────────────┘

  ※ 시청자 10배 → WebRTC 비용 10배, CDN 비용 2~3배
```

### 1.2.2 텍스트 기반 실시간 메시징

채팅, 알림, 실시간 데이터 업데이트에는 WebSocket이 훨씬 적합하다.

```
[채팅 서비스 구현 비교]

  WebRTC DataChannel                 WebSocket
  ─────────────────                  ─────────
  Signaling 서버 필요 ─────────── ─  서버 하나로 충분
  ICE 연결 수립 필요  ─────────── ─  TCP 핸드셰이크만
  STUN/TURN 인프라    ─────────── ─  불필요
  P2P (서버 제어 어려움) ────────── ─ 서버 경유 (필터링/로깅 가능)

  결론: 채팅에 WebRTC는 과잉 설계
```

WebSocket은 신뢰성 있는 순서 보장 전송을 제공하고, 서버에서 메시지를 필터링·저장·라우팅할 수 있다. "**실시간 애플리케이션의 90%는 WebSocket으로 충분하다.**"

### 1.2.3 서버→클라이언트 단방향 푸시

주식 시세, 대시보드 갱신, 뉴스 피드, AI 응답 스트리밍처럼 **서버에서 클라이언트로만** 데이터를 보내는 경우다. Server-Sent Events(SSE)가 가장 단순한 선택이다.

```
[SSE vs WebSocket vs WebRTC]

  요구사항: 서버 → 클라이언트 단방향 푸시

  SSE                    WebSocket              WebRTC
  ├── HTTP 기반          ├── 전이중 TCP          ├── P2P UDP
  ├── 방화벽 문제 없음    ├── 양방향 가능         ├── NAT 우회 필요
  ├── 자동 재연결         ├── 직접 구현           ├── ICE/STUN/TURN
  ├── CDN 호환           ├── 프록시 설정 필요     ├── Signaling 필요
  └── 구현 10줄          └── 구현 50줄           └── 구현 300줄+

  → SSE가 정답
```

### 1.2.4 지연 허용 대규모 배포

5~30초 지연이 허용되는 콘텐츠(스포츠 중계, 교육, 엔터테인먼트)에 WebRTC를 쓰면 **비용만 높고 이점은 없다**. HLS/DASH의 CDN 캐싱이 압도적으로 유리하다.

### 1.2.5 기업 방화벽 환경

기업 내부망은 HTTP/HTTPS 외의 프로토콜을 차단하는 경우가 많다. WebRTC는 UDP를 사용하므로 TURN 서버를 통한 TCP 폴백이 필요하고, 이는 추가 비용과 지연을 초래한다. HTTP 기반 기술(SSE, WebSocket over HTTPS, HLS)은 방화벽을 자연스럽게 통과한다.

# 2. 대안 기술 총정리

## 2.1 기술별 포지셔닝

```
[지연 시간 × 확장성 매트릭스]

  지연 시간
  (낮을수록 좋음)
    │
    │  WebRTC ●              ← 초저지연, 소규모
    │           WebTransport ●  ← 저지연, 클라이언트-서버
    │
    │  WebSocket ●           ← 저지연, 중규모
    │
    │     LL-HLS ●           ← 준실시간, 대규모
    │     LL-DASH ●
    │
    │  HLS/DASH ●            ← 고지연, 초대규모
    │
    └───────────────────────────── 확장성 (높을수록 좋음)
```

## 2.2 프로토콜 비교표

| 기술 | 방향 | 지연 | 확장성 | 복잡도 | 적합한 용도 |
|------|------|------|--------|--------|------------|
| **WebRTC** | 양방향 (P2P) | < 300ms | 낮음 (SFU 필요) | 매우 높음 | 1:1 영상통화, 소규모 회의 |
| **WebSocket** | 양방향 (서버경유) | 50~100ms | 중간 | 중간 | 채팅, 게임, 협업 도구 |
| **SSE** | 단방향 (서버→클라이언트) | 50~100ms | 높음 | 매우 낮음 | 알림, 대시보드, AI 스트리밍 |
| **HLS** | 단방향 (서버→클라이언트) | 15~30초 | 매우 높음 (CDN) | 낮음 | 대규모 라이브, VOD |
| **LL-HLS** | 단방향 (서버→클라이언트) | 2~5초 | 매우 높음 (CDN) | 낮음 | 인터랙티브 라이브 |
| **DASH** | 단방향 (서버→클라이언트) | 10~30초 | 매우 높음 (CDN) | 낮음 | 크로스 플랫폼 스트리밍 |
| **LL-DASH** | 단방향 (서버→클라이언트) | 2~3초 | 매우 높음 (CDN) | 낮음 | 저지연 대규모 방송 |
| **RTMP** | 단방향 (클라이언트→서버) | 1~3초 | 낮음 | 중간 | 방송 인제스트 (송출) |
| **WebTransport** | 양방향 (서버경유) | < 100ms | 중간 | 중간~높음 | 게임, IoT, 커스텀 미디어 |

# 3. 프로토콜별 심층 비교

## 3.1 WebRTC vs WebSocket

가장 흔한 혼동이다. 둘 다 "실시간"이지만 목적이 다르다.

```
[WebRTC vs WebSocket 아키텍처]

  WebRTC                              WebSocket
  ──────                              ─────────
  브라우저 A ←──── P2P ────→ 브라우저 B    클라이언트 A ←→ 서버 ←→ 클라이언트 B

  ┌──────────────────┐                ┌──────────────────┐
  │ 전송: UDP (SRTP)  │                │ 전송: TCP         │
  │ 미디어: 내장 코덱  │                │ 미디어: 없음       │
  │ NAT: ICE 자동 우회 │                │ NAT: 서버 경유    │
  │ 암호화: DTLS+SRTP │                │ 암호화: TLS (WSS) │
  │ 신뢰성: 비보장     │                │ 신뢰성: TCP 보장   │
  └──────────────────┘                └──────────────────┘
```

**WebSocket을 선택해야 하는 경우:**

- 텍스트/JSON 메시지 교환 (채팅, 알림)
- 서버에서 메시지 라우팅·필터링·저장이 필요한 경우
- 메시지 순서 보장과 신뢰성 전달이 필수인 경우
- 미디어 스트리밍이 아닌 데이터 통신인 경우

**WebRTC를 선택해야 하는 경우:**

- 음성/영상 실시간 통화
- P2P 직접 연결로 서버 부하를 줄이고 싶은 경우
- 300ms 미만 초저지연이 필수인 경우

## 3.2 WebRTC vs HLS/DASH

스트리밍 프로토콜의 양대 진영이다.

```
[동작 원리 비교]

  WebRTC (실시간)                     HLS/DASH (세그먼트 기반)
  ─────────────                      ──────────────────────
  인코더 → RTP 패킷 → SFU → 시청자    인코더 → 세그먼트 파일 → CDN → 시청자

  패킷 단위 전송                      6~10초 세그먼트 단위 전송
  ├── 프레임 즉시 전달                 ├── 세그먼트 완성 후 전달
  ├── 패킷 손실 시 건너뜀              ├── HTTP 재요청으로 복구
  └── 버퍼 최소화                     └── 버퍼 유지 (안정성)

  ┌─────────────────────────────────────────────────────┐
  │                  지연 시간 스펙트럼                    │
  │                                                     │
  │  WebRTC     WebTransport   LL-HLS    HLS    DASH    │
  │  |           |              |         |       |     │
  │  ├──────────┼──────────────┼─────────┼───────┤     │
  │  0       500ms            3초      15초    30초     │
  │                                                     │
  │  ◀── 실시간 ──▶  ◀── 준실시간 ──▶  ◀── 비실시간 ──▶  │
  └─────────────────────────────────────────────────────┘
```

### 3.2.1 HLS 동작 원리

HLS(HTTP Live Streaming)는 Apple이 2009년에 개발한 프로토콜이다.

```
[HLS 세그먼트 방식]

  인코더                        CDN                  클라이언트
    │                           │                      │
    │── 6초 세그먼트 생성 ────→  │                      │
    │   (segment_001.ts)        │── 캐싱 ──→           │
    │                           │              ←── m3u8 요청
    │── 6초 세그먼트 생성 ────→  │              ←── 세그먼트 요청
    │   (segment_002.ts)        │── 캐싱 ──→           │
    │                           │              ←── 세그먼트 요청
    ...                         ...                    ...

  m3u8 (매니페스트 파일):
  ┌─────────────────────────────────┐
  │ #EXTM3U                         │
  │ #EXT-X-TARGETDURATION:6         │
  │ #EXT-X-MEDIA-SEQUENCE:101       │
  │ #EXTINF:6.0,                    │
  │ segment_101.ts                  │
  │ #EXTINF:6.0,                    │
  │ segment_102.ts                  │
  │ #EXTINF:6.0,                    │
  │ segment_103.ts                  │
  └─────────────────────────────────┘

  지연 = 세그먼트 길이 × 3(버퍼) + 인코딩 = 약 20~30초
```

### 3.2.2 LL-HLS (Low-Latency HLS)

Apple이 2019년 도입한 LL-HLS는 **부분 세그먼트**로 지연을 2~5초로 줄인다.

```
[LL-HLS vs 기존 HLS]

  기존 HLS:
    [===== 6초 세그먼트 =====] → CDN → 플레이어
    지연: 15~30초

  LL-HLS:
    [=1=][=2=][=3=][=4=][=5=][=6=]  ← 1초 부분 세그먼트
      ↓    ↓    ↓    ↓    ↓    ↓
     CDN  CDN  CDN  CDN  CDN  CDN   ← 즉시 전달
    지연: 2~5초

  핵심 기술:
  ├── Partial Segments: 세그먼트 완성 전 부분 전달
  ├── Blocking Playlist: 새 콘텐츠까지 응답 대기 (폴링 제거)
  └── CMAF: 청크 단위 전송 가능한 컨테이너 포맷
```

### 3.2.3 비용과 확장성 비교

| 항목 | WebRTC (SFU) | HLS/DASH (CDN) |
|------|-------------|----------------|
| **100명 시청, 1시간** | ~$10~50 | ~$2~10 |
| **10,000명 시청, 1시간** | ~$1,000~5,000 | ~$20~100 |
| **100만 명 시청, 1시간** | 사실상 불가능 | ~$2,000~10,000 |
| **비용 증가 패턴** | 시청자 비례 선형 증가 | CDN 캐싱으로 완만한 증가 |
| **ABR (적응형 비트레이트)** | 제한적 (Simulcast) | 완전 지원 |
| **DVR/되감기** | 미지원 | 기본 지원 |
| **DRM** | 미지원 | 지원 |

## 3.3 WebRTC vs RTMP

RTMP(Real-Time Messaging Protocol)는 Adobe가 개발한 프로토콜로, **방송 인제스트(송출)** 표준이다.

```
[스트리밍 파이프라인에서의 위치]

  방송자                   서버                    시청자
  ┌──────┐              ┌──────┐              ┌──────┐
  │ OBS  │── RTMP ──→   │트랜스│── HLS  ──→   │ CDN  │──→ 시청자들
  │ 카메라│  (인제스트)   │코딩  │── DASH ──→   │      │
  └──────┘              │서버  │              └──────┘
                        └──────┘
                           │
                           └── WebRTC ──→ 소수 인터랙티브 시청자

  RTMP: 방송자 → 서버 (인제스트 전용, 1~3초 지연)
  HLS:  서버 → 시청자 (대규모 배포, 2~30초 지연)
  WebRTC: 서버 ↔ 시청자 (소규모 인터랙티브, < 300ms 지연)
```

RTMP는 시청자 배포용이 아니라 **서버로의 송출용**이다. 최근에는 WHIP(WebRTC-HTTP Ingestion Protocol)가 RTMP를 대체하려는 움직임이 있다.

## 3.4 WebRTC vs SSE (Server-Sent Events)

```
[SSE 코드 예시 - 클라이언트]

  // 서버 → 클라이언트 단방향 스트림 (3줄이면 충분)
  const source = new EventSource('/api/stream');
  source.onmessage = (e) => console.log(e.data);
  source.onerror = () => console.log('자동 재연결 중...');
```

```
[SSE 코드 예시 - Golang 서버]

  func streamHandler(w http.ResponseWriter, r *http.Request) {
      w.Header().Set("Content-Type", "text/event-stream")
      w.Header().Set("Cache-Control", "no-cache")

      flusher := w.(http.Flusher)
      for {
          fmt.Fprintf(w, "data: %s\n\n", time.Now().Format(time.RFC3339))
          flusher.Flush()
          time.Sleep(1 * time.Second)
      }
  }
```

SSE의 장점은 **단순함**이다. HTTP 기반이므로 방화벽, CDN, 로드밸런서와 자연스럽게 호환되고, 브라우저가 자동 재연결을 처리한다. "**실시간 애플리케이션의 95%는 서버→클라이언트 단방향 업데이트만 필요하다.**"

# 4. 기술 선택 의사결정 트리

## 4.1 핵심 질문 3가지

기술 선택은 **세 가지 질문**으로 결정된다.

```
[의사결정 질문]

  Q1. 양방향 미디어 통신이 필요한가?
      │
      ├── Yes → Q2로
      └── No  → Q3으로

  Q2. 참가자가 몇 명인가?
      │
      ├── 1:1 또는 소규모 (< 50명)  → WebRTC
      ├── 중규모 (50~1,000명)       → WebRTC + SFU
      └── 대규모 (> 1,000명)        → WebRTC 인제스트 + HLS/DASH 배포

  Q3. 지연 허용 범위는?
      │
      ├── < 500ms  (실시간)    → WebRTC 또는 WebTransport
      ├── 2~5초   (준실시간)   → LL-HLS / LL-DASH
      └── 5초 이상 (비실시간)   → HLS / DASH
```

## 4.2 상세 의사결정 트리

```
[기술 선택 플로우차트]

  시작: 어떤 종류의 통신인가?

    │     │
    │     ├── 1:1 통화 ──────────────────→ WebRTC (P2P)
    │     ├── 소규모 회의 (2~50명) ───────→ WebRTC (SFU)
    │     └── 대규모 웨비나 (50명+) ──────→ WebRTC(발표자) + HLS(시청자)
    │
    ├── 라이브 스트리밍 (단방향 영상)
    │     │
    │     ├── 지연 < 500ms 필요
    │     │     ├── 시청자 < 1,000명 ────→ WebRTC (SFU)
    │     │     └── 시청자 > 1,000명 ────→ WebRTC + CDN 하이브리드
    │     │
    │     ├── 지연 2~5초 허용

    │           └── ─────────────────────→ HLS 또는 DASH
    │
    ├── 데이터 통신 (텍스트/JSON)
    │     │
    │     ├── 양방향 필요
    │     │     ├── P2P 필수 ─────────────→ WebRTC DataChannel
    │     │     └── 서버 경유 가능 ────────→ WebSocket
    │     │
    │     └── 서버→클라이언트만
    │           └── ─────────────────────→ SSE
    │
    └── 파일 전송
          │
          ├── P2P 직접 전송 필요 ─────────→ WebRTC DataChannel
          └── 서버 경유 가능 ──────────────→ HTTP Upload/Download
```

## 4.3 실시간 vs 준실시간 판단 기준

"실시간"이라는 단어를 쓸 때 정확히 어떤 지연 범위를 의미하는지 구분해야 한다.

| 구분 | 지연 범위 | 사용자 체감 | 적합 기술 | 대표 사례 |
|------|----------|-----------|----------|----------|
| **실시간** | < 300ms | 대화가 자연스러움 | WebRTC | 영상통화, 원격 제어 |
| **거의 실시간** | 300ms~2초 | 약간의 지연 인지 | WebRTC(SFU), WebTransport | 라이브 경매, 게임 |
| **준실시간** | 2~5초 | 지연 인지하지만 수용 | LL-HLS, LL-DASH | 스포츠 중계, 라이브 커머스 |
| **비실시간** | 5~30초 | 명확한 지연 | HLS, DASH | TV 중계, 교육, VOD |

**핵심 기준**: "시청자가 방송자에게 **즉각 반응**해야 하는가?"

- Yes → 실시간 (WebRTC)
- 채팅으로 반응하면 충분 → 준실시간 (LL-HLS)
- 반응이 불필요 → 비실시간 (HLS/DASH)

  ┌─────────────────────────────────────────────────────────────┐
  │  서비스        인제스트       서버          배포              │
  ├─────────────────────────────────────────────────────────────┤

  │  Zoom         커스텀    →  SFU        →  커스텀 (RTP 기반)   │

## 5.2 왜 이렇게 선택했는가

### 5.2.1 Twitch: RTMP + LL-HLS

Twitch는 수백만 동시 시청자를 처리해야 한다. WebRTC로는 불가능한 규모다.

```
[Twitch 아키텍처]

  방송자 (OBS)                    Twitch 서버             시청자 (수백만)
  ┌────────┐                    ┌───────────┐           ┌──────────┐
  │ RTMP   │── 1~3초 지연 ──→   │ 트랜스코딩 │── CDN ──→ │ LL-HLS   │
  │ 인제스트│                    │ 1080p     │           │ 2~3초    │
  └────────┘                    │  720p     │           │ 지연     │
                                │  480p     │           └──────────┘
                                └───────────┘
                                      │
                                 ABR 지원: 시청자 네트워크에
                                 따라 자동 화질 전환

  선택 이유:
  ├── CDN으로 수백만 명 동시 서비스 가능
  ├── ABR로 다양한 네트워크 환경 대응
  ├── 2~3초 지연은 채팅 인터랙션에 충분
  └── 인프라 비용이 WebRTC 대비 1/10 이하
```

### 5.2.2 Google Meet: 순수 WebRTC

Google Meet은 양방향 영상통화가 핵심이다. 모든 참가자가 동시에 말하고 들어야 한다.

```
[Google Meet 아키텍처]

  참가자 A ──┐                    ┌── 참가자 C
             │                    │
             ▼                    ▼
         ┌──────────────────────────┐
         │         SFU 서버         │
         │  ├── 스트림 선택적 전달   │
         │  ├── Simulcast 수신      │
         │  └── Active Speaker 감지 │
         └──────────────────────────┘
             ▲                    ▲
             │                    │
  참가자 B ──┘                    └── 참가자 D

  선택 이유:
  ├── 양방향 통신 필수 (WebRTC만 가능)
  ├── < 200ms 지연 (자연스러운 대화)
  ├── 최대 500명 (기업용)
  └── Google이 WebRTC를 만들었으므로 자사 기술 활용
```

### 5.2.3 하이브리드 패턴: WebRTC + HLS

대부분의 대규모 인터랙티브 스트리밍은 **하이브리드 구조**를 사용한다.

```
[하이브리드 아키텍처]

  방송자                    서버                      시청자
  ┌──────┐              ┌──────────┐
  │WebRTC│── 인제스트 ──→│ 미디어   │──→ WebRTC ──→ VIP 시청자 (< 100명)
  │      │              │ 서버     │                 (초저지연, 양방향)
  └──────┘              │          │
                        │          │──→ HLS/CDN ──→ 일반 시청자 (수만 명)
  공동 방송자             │          │                 (2~5초 지연, 단방향)
  ┌──────┐              │          │
  │WebRTC│── 양방향 ────→│          │
  └──────┘              └──────────┘

  사용 사례:
  ├── 라이브 경매: 입찰자(WebRTC) + 관전자(HLS)
  ├── 라이브 커머스: 판매자(WebRTC) + 구매자(LL-HLS)
  └── 교육: 강사+질문자(WebRTC) + 청강생(HLS)
```

# 6. 새로운 표준과 미래

## 6.1 WHIP / WHEP

WHIP(WebRTC-HTTP Ingestion Protocol)과 WHEP(WebRTC-HTTP Egress Protocol)는 WebRTC의 **Signaling 복잡도**를 해결한다.

```
[기존 WebRTC Signaling vs WHIP/WHEP]

  기존 WebRTC:
    클라이언트                     서버
       │── WebSocket 연결 ──────→ │
       │← ──────── 연결 확인 ──── │
       │── SDP Offer ───────────→ │
       │← ── SDP Answer ──────── │
       │── ICE Candidate 1 ─────→ │
       │── ICE Candidate 2 ─────→ │
       │← ── ICE Candidate 1 ─── │
       │← ── ICE Candidate 2 ─── │
       │   (여러 번 왕복...)       │
       └── 연결 수립 ─────────────┘
       → 커스텀 Signaling 서버 필요

  WHIP (인제스트):
    방송자                         서버
       │── POST /whip              │
       │   (SDP Offer + 인증)      │
       │← ── 201 Created ──────── │
       │   (SDP Answer)            │
       └── 연결 수립 ─────────────┘
       → 표준 HTTP 엔드포인트 하나로 충분

  WHEP (시청):
    시청자                         서버
       │── POST /whep              │
       │   (SDP Offer)             │
       │← ── 201 Created ──────── │
       │   (SDP Answer)            │
       └── 연결 수립 ─────────────┘
       → 표준 HTTP 엔드포인트 하나로 충분
```

**WHIP** (RFC 9725, 2025년 3월 표준화):

- RTMP를 대체하는 초저지연 인제스트 프로토콜
- OBS Studio, Cloudflare Stream 등에서 이미 지원
- 단일 HTTP POST로 Signaling 완료

**WHEP** (Internet-Draft, 표준화 진행 중):

- WebRTC 기반 표준화된 시청 프로토콜
- 범용 WebRTC 플레이어 구현 가능
- Bearer 토큰 인증으로 기존 인프라와 통합 용이

## 6.2 WebTransport

WebTransport는 HTTP/3(QUIC) 위에 구축된 **클라이언트-서버 실시간 통신** 프로토콜이다.

```
[WebRTC vs WebTransport]

  WebRTC                              WebTransport
  ──────                              ────────────
  목적: P2P 미디어 통신                목적: 클라이언트-서버 데이터 통신
  전송: SRTP/SCTP over DTLS           전송: QUIC (HTTP/3)
  설정: SDP + ICE + STUN/TURN         설정: HTTP/3 연결 (설정 불필요)
  미디어: 코덱, 에코 제거 내장          미디어: 없음 (WebCodecs와 조합)
  HOL 블로킹: 부분적                   HOL 블로킹: 없음 (QUIC)
  브라우저: 전체 지원                   브라우저: Chrome, Firefox (Safari 미지원)

  WebTransport가 더 나은 경우:
  ├── 서버-클라이언트 구조 (P2P 불필요)
  ├── 게임 상태 동기화
  ├── IoT 텔레메트리
  └── 커스텀 미디어 파이프라인 (WebCodecs 조합)

  WebRTC가 여전히 필요한 경우:
  ├── 브라우저 간 P2P 통신
  ├── 내장 미디어 스택 (코덱, 에코 제거)
  └── 전체 브라우저 호환성
```

WebTransport의 핵심 이점은 **ICE/STUN/TURN 인프라가 불필요**하다는 것이다. HTTP/3 연결을 그대로 사용하므로 연결 설정이 극적으로 단순해진다. 다만 미디어 처리 스택이 없으므로 영상통화에는 적합하지 않다.

## 6.3 MoQ (Media over QUIC)

MoQ는 WebRTC의 초저지연과 HLS/DASH의 확장성을 **동시에 달성**하려는 새로운 표준이다.

```
[MoQ 포지셔닝]

  지연 시간       확장성        MoQ의 위치
  ──────────     ──────────   ────────────

  WebRTC ●       HLS/DASH ●
  (< 300ms)      (수백만)
       \            /
        \          /
         \        /
          ● MoQ
    (< 1초, 대규모 CDN 가능)

  MoQ 핵심 특징:
  ├── QUIC 기반 Pub/Sub 모델
  ├── CDN 릴레이 네이티브 지원
  ├── 되감기/DVR 기능 내장
  └── 목표: 2030년까지 라이브 스트리밍 표준
```

MoQ는 아직 초기 단계(IETF Working Group)이지만, WebRTC와 HLS 사이의 간극을 메우는 유망한 기술이다.

# 7. 최종 선택 가이드

## 7.1 한눈에 보는 선택 매트릭스

| 시나리오 | 추천 기술 | 이유 |
|---------|----------|------|
| **1:1 영상통화** | WebRTC | 양방향 미디어, 초저지연 |

| **대규모 라이브 방송** | RTMP(인제스트) + HLS(배포) | CDN 확장성, 검증된 아키텍처 |
| **초저지연 라이브 방송** | WHIP(인제스트) + WHEP(시청) | RTMP 대체, 표준화된 WebRTC |
| **실시간 채팅** | WebSocket | 신뢰성, 서버 제어, 단순함 |
| **알림/대시보드** | SSE | 가장 단순, HTTP 호환 |
| **게임 상태 동기화** | WebSocket 또는 WebTransport | 서버 권위 모델, 저지연 |
| **P2P 파일 전송** | WebRTC DataChannel | 서버 비용 제거, 직접 전송 |
| **원격 로봇 제어** | WebRTC (미디어+DataChannel) | 영상+제어 동시, 초저지연 |
| **VOD 서비스** | HLS 또는 DASH | CDN, ABR, DRM 지원 |

[기술 선택 체크리스트]

  □ 1. 통신 방향은?

       ├── < 300ms → WebRTC 필수

       └── > 5초   → HLS/DASH 충분

  □ 3. 동시 사용자 수는?
       ├── < 50명   → WebRTC P2P 또는 SFU

       └── > 1,000명 → HLS/DASH 또는 하이브리드

  □ 4. 인프라 예산은?
       ├── 최소 비용 → SSE, WebSocket, HLS

  □ 5. 브라우저 호환성 요구사항은?
       ├── 모든 브라우저 → WebRTC, HLS, WebSocket
       └── 모던 브라우저만 → WebTransport 가능

  □ 6. 기업 방화벽 환경에서 동작해야 하는가?
       ├── Yes → HTTP 기반 (HLS, SSE, WebSocket over HTTPS)
       └── No  → 제한 없음

  □ 7. 기존 CDN 인프라를 활용할 수 있는가?
       ├── Yes → HLS/DASH 우선 검토
       └── No  → WebRTC도 가능
```

  └── 편 12. 보안과 운영

  5단계: 판단력
  └── 편 13. 기술 선택 가이드 (본 편) ← 지금 여기
```

WebRTC를 깊이 이해한 사람만이 "**이 상황에서는 WebRTC가 아니라 HLS가 맞다**"고 판단할 수 있다. 기술을 제대로 아는 것과 적재적소에 쓰는 것은 별개의 역량이다. 이 시리즈가 두 가지 모두에 도움이 되었기를 바란다.
