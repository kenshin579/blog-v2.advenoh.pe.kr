WebRTC(Web Real-Time Communication)는 브라우저와 모바일 앱에서 **플러그인 없이** 실시간 음성, 영상, 데이터 통신을 가능하게 하는 기술이다. Google Meet, Discord, Facebook Messenger 등 우리가 매일 사용하는 서비스 뒤에는 WebRTC가 있다. 이 글에서는 WebRTC가 무엇이고, 왜 필요하며, 어떤 구조로 동작하는지 전체적인 그림을 잡아본다.

# 1. WebRTC란 무엇인가

WebRTC는 **API이자 프로토콜**이다. 이 두 가지를 구분하는 것이 중요하다.

- **WebRTC 프로토콜**: 두 에이전트(Agent) 간 실시간 양방향 보안 통신을 위한 규칙의 집합이다. IETF의 `rtcweb` 작업 그룹에서 관리한다.
- **WebRTC API**: 개발자가 WebRTC 프로토콜을 사용할 수 있게 해주는 JavaScript API이다. W3C에서 관리한다.

HTTP와 Fetch API의 관계를 생각하면 이해하기 쉽다. HTTP가 프로토콜이고 Fetch API가 이를 사용하는 JavaScript API인 것처럼, WebRTC도 동일한 구조이다.

```
┌─────────────────────────────┐
│       WebRTC API (W3C)      │  ← JavaScript로 제어
├─────────────────────────────┤
│   WebRTC 프로토콜 (IETF)     │  ← 실제 통신 규칙
├─────────────────────────────┤
│   UDP / TCP / Network       │
└─────────────────────────────┘
```

WebRTC 프로토콜은 JavaScript 외에도 다양한 언어로 구현되어 있다. 대표적으로 Go 언어의 [Pion](https://github.com/pion/webrtc), C/C++의 [libwebrtc](https://webrtc.googlesource.com/src/), Rust의 [webrtc-rs](https://github.com/webrtc-rs/webrtc) 등이 있다. 어떤 구현체를 사용하든 프로토콜이 동일하기 때문에 **상호운용성이 보장**된다.

# 2. 왜 WebRTC를 사용하는가

## 2.1 기존 통신 기술의 한계

실시간 통신을 구현할 때 흔히 떠올리는 기술은 HTTP와 WebSocket이다. 그러나 이 기술들은 실시간 미디어 전송에 근본적인 한계가 있다.

### 2.1.1 HTTP의 한계

HTTP는 요청-응답(Request-Response) 기반이다. 클라이언트가 요청해야만 서버가 응답하는 구조이기 때문에 **실시간 양방향 통신에 적합하지 않다**. Long Polling이나 SSE(Server-Sent Events)로 보완할 수 있지만, 근본적으로 단방향이다.

### 2.1.2 WebSocket의 한계

WebSocket은 양방향 통신이 가능하지만 다음과 같은 한계가 있다.

| 항목 | WebSocket | WebRTC |
|------|-----------|--------|
| 연결 방식 | 클라이언트 → 서버 (항상 서버 경유) | P2P 직접 연결 가능 |
| 지연 시간 | 서버 경유로 인한 추가 지연 | 직접 연결로 최소 지연 |
| 미디어 지원 | 직접 구현 필요 | 내장 (코덱, 혼잡 제어 등) |
| NAT 통과 | 별도 처리 없음 (서버 경유이므로) | ICE/STUN/TURN으로 자동 처리 |
| 암호화 | 선택 (wss://) | 필수 (DTLS/SRTP) |
| 프로토콜 | TCP 기반 | UDP 기반 (실시간에 유리) |

WebSocket은 채팅, 알림 같은 텍스트 기반 실시간 통신에는 충분하다. 하지만 영상/음성 같은 미디어 스트리밍에서는 TCP의 재전송 메커니즘이 오히려 지연을 증가시키는 문제가 있다.

## 2.2 WebRTC의 장점

WebRTC는 이러한 한계를 해결하기 위해 설계되었다. 주요 장점은 다음과 같다.

### 개방형 표준

WebRTC는 IETF와 W3C에 의해 관리되는 공개 표준이다. 특정 벤더에 종속되지 않으며, 누구나 구현하고 사용할 수 있다.

### P2P 직접 연결

중앙 서버 없이 두 에이전트가 직접 통신할 수 있다. 서버를 경유하지 않기 때문에 지연 시간이 최소화되고 서버 비용도 줄어든다.

### 1초 미만의 초저지연

UDP 기반 전송과 P2P 연결을 통해 **수백 밀리초 수준의 지연**을 달성한다. 화상회의나 원격 제어처럼 즉각적인 반응이 필요한 서비스에 적합하다.

### 의무적 암호화

WebRTC는 DTLS(Datagram Transport Layer Security)와 SRTP(Secure Real-time Transport Protocol)를 사용하여 **모든 통신을 암호화**한다. 선택이 아니라 필수이기 때문에 보안이 기본적으로 보장된다.

### NAT 자동 통과

대부분의 사용자는 공유기(NAT) 뒤에 있어 외부에서 직접 접근할 수 없다. WebRTC는 ICE, STUN, TURN 프로토콜을 통해 이 문제를 자동으로 해결한다.

### 혼잡 제어

네트워크 상태에 따라 비트레이트와 해상도를 자동으로 조절한다. 네트워크가 나빠지면 화질을 낮추고, 좋아지면 다시 높이는 적응형 전송이 내장되어 있다.

### 기존 기술 재활용

WebRTC는 완전히 새로운 기술이 아니다. SDP, ICE, STUN, TURN, RTP, SRTP, SCTP 등 이미 검증된 프로토콜들을 조합한 것이다.

# 3. WebRTC가 해결하려는 문제

WebRTC가 해결하는 핵심 문제 두 가지를 이해하면, 나머지 기술적 세부사항이 자연스럽게 따라온다.

## 3.1 실시간성 (Latency)

일반적인 비디오 스트리밍 서비스(YouTube, Netflix 등)는 HLS나 DASH 프로토콜을 사용한다. 이 방식은 영상을 수 초 단위의 세그먼트로 나누어 전송하기 때문에 **3~30초의 지연**이 발생한다.

```
[일반 스트리밍]
촬영 → 인코딩 → 세그먼트 분할 → CDN 배포 → 클라이언트 버퍼 → 재생
                        (3~30초 지연)

[WebRTC]
촬영 → 인코딩 → RTP 패킷 전송 → 수신 → 재생
              (100~500ms 지연)
```

WebRTC는 UDP 기반의 RTP 프로토콜로 미디어를 전송하여 1초 미만의 지연을 달성한다. TCP와 달리 UDP는 패킷 손실 시 재전송을 기다리지 않기 때문에 실시간성을 유지할 수 있다.

## 3.2 NAT / 방화벽 통과

인터넷에 연결된 대부분의 기기는 NAT(Network Address Translation) 뒤에 있다. 집에서 사용하는 공유기가 대표적인 NAT 장비이다.

```
[NAT 뒤의 네트워크 구조]

  사설 네트워크 (192.168.x.x)         인터넷
┌──────────────────────┐       ┌──────────────────┐
│  PC (192.168.1.10)   │       │                  │
│  Phone (192.168.1.11)│──NAT──│  공인 IP (1.2.3.4)│
│  Tablet (192.168.1.12)│      │                  │
└──────────────────────┘       └──────────────────┘
```

NAT 뒤에 있는 기기는 외부에서 직접 접근할 수 없다. 내가 상대방의 사설 IP(192.168.1.10)를 알아도 공유기가 차단하기 때문이다. WebRTC는 이 문제를 ICE 프레임워크로 해결한다.

1. **STUN 서버**: 내 기기의 공인 IP와 포트를 알려준다
2. **TURN 서버**: 직접 연결이 불가능할 때 중계 서버 역할을 한다
3. **ICE**: STUN과 TURN을 조합하여 최적의 연결 경로를 찾는다

이 내용은 시리즈 3편(핵심 개념 정리)에서 자세히 다룬다.

# 4. WebRTC 프로토콜 4단계 구조

WebRTC의 전체 동작을 이해하려면 4단계 구조를 머릿속에 그릴 수 있어야 한다. 각 단계는 순서대로 진행된다.

```
┌─────────────────────────────────────────────┐
│  1단계: 시그널링 (Signaling)                   │
│  - SDP 교환 (Offer/Answer)                    │
│  - 코덱, IP, 포트 정보 공유                     │
├─────────────────────────────────────────────┤
│  2단계: 연결 (Connecting)                      │
│  - ICE를 통한 최적 경로 탐색                     │
│  - STUN/TURN으로 NAT 통과                     │
├─────────────────────────────────────────────┤
│  3단계: 보안 (Securing)                        │
│  - DTLS 핸드셰이크 (키 교환 + 상호 인증)          │
│  - SRTP 암호화 설정                            │
├─────────────────────────────────────────────┤
│  4단계: 통신 (Communicating)                   │
│  - 미디어: RTP/SRTP                           │
│  - 데이터: SCTP (DataChannel)                  │
└─────────────────────────────────────────────┘
```

## 4.1 1단계: 시그널링 (Signaling)

WebRTC 에이전트는 시작 시점에 **상대방에 대해 아무것도 모른다**. 누구와 통신할지, 어떤 코덱을 지원하는지, IP 주소가 무엇인지 알 수 없다. 이 정보를 교환하는 과정이 시그널링이다.

시그널링은 **SDP(Session Description Protocol)**라는 평문 텍스트 프로토콜을 사용한다. SDP에는 다음 정보가 포함된다.

- 접근 가능한 IP와 포트 (ICE 후보)
- 오디오/비디오 트랙 수
- 지원하는 코덱 목록
- 연결 설정값
- 보안 인증서 정보 (fingerprint)

시그널링은 Offer/Answer 모델로 동작한다.

```
  Peer A (Offerer)              Signaling Server              Peer B (Answerer)
       │                              │                              │
       │──── 1. Offer (SDP) ──────────>│                              │
       │                              │──── 2. Offer 전달 ────────────>│
       │                              │                              │
       │                              │<──── 3. Answer (SDP) ────────│
       │<──── 4. Answer 전달 ──────────│                              │
       │                              │                              │
```

중요한 점은 **시그널링은 WebRTC 스펙에 포함되지 않는다**는 것이다. SDP를 어떻게 전달할지는 개발자가 자유롭게 결정할 수 있다. WebSocket, HTTP API, 심지어 MQTT도 사용할 수 있다. 이 유연성 덕분에 기존 인프라를 그대로 활용할 수 있다.

## 4.2 2단계: 연결 (Connecting)

시그널링을 통해 서로의 정보를 교환했다면, 이제 실제로 네트워크 연결을 수립해야 한다. ICE(Interactive Connectivity Establishment)가 이 과정을 담당한다.

ICE는 두 에이전트 간 통신 가능한 **모든 경로(후보)**를 수집하고, 그 중 최적의 경로를 선택한다.

후보의 종류는 다음과 같다.

| 후보 유형 | 설명 | 우선순위 |
|-----------|------|----------|
| Host | 자신의 로컬 IP | 최고 (직접 연결) |
| Server Reflexive | STUN을 통해 알게 된 공인 IP | 중간 |
| Relay | TURN 서버를 경유하는 주소 | 최저 (모든 트래픽 중계) |

ICE는 우선순위가 높은 후보부터 시도하여, 연결 가능한 가장 효율적인 경로를 사용한다.

## 4.3 3단계: 보안 (Securing)

연결이 수립되면 DTLS(Datagram Transport Layer Security) 핸드셰이크가 진행된다. DTLS는 TLS의 UDP 버전으로, 키 교환과 상호 인증을 수행한다.

- 미디어 통신: SRTP(Secure Real-time Transport Protocol)로 암호화
- 데이터 통신: DTLS 위의 SCTP로 보호

시그널링 단계에서 교환한 인증서의 fingerprint를 DTLS 핸드셰이크에서 검증하기 때문에, 중간자 공격(MITM)을 방지할 수 있다.

## 4.4 4단계: 통신 (Communicating)

보안 연결이 완료되면 실제 데이터 전송이 시작된다. WebRTC는 두 가지 채널을 제공한다.

### 미디어 채널 (RTP/SRTP)

음성과 영상 데이터를 전송한다. RTP(Real-time Transport Protocol)는 실시간 미디어 전송에 최적화된 프로토콜로, 타임스탬프, 시퀀스 번호, 페이로드 타입 등을 포함한다.

### 데이터 채널 (SCTP/DataChannel)

임의의 데이터를 전송한다. SCTP(Stream Control Transmission Protocol) 기반으로, TCP처럼 순서 보장과 신뢰성을 제공할 수도 있고, UDP처럼 비순서/비신뢰 전송도 선택할 수 있다.

```
                    WebRTC 통신 채널
                         │
            ┌────────────┼────────────┐
            │                         │
     미디어 채널                   데이터 채널
    (RTP/SRTP)                 (SCTP/DataChannel)
            │                         │
    ┌───────┼───────┐         ┌───────┼───────┐
    │               │         │               │
  Audio          Video     순서 보장      비순서 전송
  (Opus)      (VP8/H.264)  (채팅 등)    (게임 상태 등)
```

# 5. 대표적인 사용 사례

## 5.1 화상회의

가장 대표적인 사용 사례이다. Google Meet, Zoom, Microsoft Teams 등이 WebRTC를 사용한다. 1:1 통화는 P2P로, 다자간 회의는 SFU(Selective Forwarding Unit) 서버를 활용한다.

## 5.2 실시간 스트리밍

Twitch, YouTube Live 등에서 초저지연 스트리밍에 활용한다. HLS/DASH 대비 10배 이상 낮은 지연 시간을 제공하여, 실시간 경매나 라이브 커머스 같은 양방향 소통이 필요한 서비스에 적합하다.

## 5.3 로봇 / 원격 제어

WebRTC의 DataChannel을 활용하면 로봇에 실시간 제어 명령을 전송하면서, 동시에 로봇의 카메라 영상을 수신할 수 있다. P2P 연결의 초저지연 특성이 원격 제어에 특히 유리하다.

```
[원격 로봇 제어 구조]

  조종자 (브라우저)                              로봇 (Golang/Pion)
┌──────────────────┐                        ┌──────────────────┐
│  제어 UI          │ ──DataChannel────────> │  모터 제어         │
│                  │   (조이스틱 입력)         │                  │
│  영상 모니터       │ <──Media Channel────── │  카메라            │
│                  │   (실시간 영상)          │                  │
│  센서 데이터 표시   │ <──DataChannel──────── │  센서 (LiDAR 등)   │
└──────────────────┘                        └──────────────────┘
```

## 5.4 P2P 파일 전송

DataChannel을 통해 서버를 거치지 않고 파일을 직접 전송할 수 있다. WebTorrent 등이 이 방식을 활용한다.

## 5.5 클라우드 게이밍

Google Stadia(종료), NVIDIA GeForce NOW 등 클라우드 게이밍 서비스에서 서버의 렌더링 결과를 클라이언트에 실시간으로 전송할 때 WebRTC를 활용한다.

# 6. WebRTC를 사용하면 안 되는 경우

모든 실시간 통신에 WebRTC가 정답은 아니다. 다음 경우에는 다른 기술이 더 적합하다.

| 상황 | 더 나은 대안 | 이유 |
|------|-------------|------|
| 채팅, 알림 | WebSocket | 텍스트 데이터에 P2P는 과하다 |
| 대규모 단방향 스트리밍 (1만+ 시청자) | HLS/DASH | CDN 활용이 효율적 |
| VOD(녹화 영상) | HLS/DASH | 실시간이 아닌 온디맨드 |
| 서버 간 통신 | gRPC, HTTP/2 | P2P/NAT 통과가 불필요 |

판단 기준은 간단하다: **"상대방의 반응이 1초 이내에 필요한가?"** 이 질문에 Yes라면 WebRTC를 고려하고, No라면 더 단순한 기술을 사용하는 것이 좋다.

# 8. 정리

- WebRTC는 **API이자 프로토콜**이다. 브라우저뿐 아니라 다양한 언어로 구현할 수 있다
- 기존 HTTP/WebSocket 대비 **P2P 직접 연결**, **초저지연**, **의무적 암호화**가 핵심 차별점이다
- 4단계 구조를 기억하자: **시그널링 → 연결 → 보안 → 통신**
- 화상회의, 실시간 스트리밍, 로봇 원격 제어, P2P 파일 전송 등에 활용된다
- 모든 실시간 통신에 WebRTC가 정답은 아니다. 요구사항에 맞는 기술을 선택해야 한다

다음 편에서는 WebRTC의 전체 구조를 더 깊이 들여다보며, Media/Transport/Signaling 각 구성 요소의 역할과 P2P, SFU, MCU 아키텍처의 차이를 알아본다.
