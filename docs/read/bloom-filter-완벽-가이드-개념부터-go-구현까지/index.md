# 1. 개요

## 1.1 Bloom Filter란

Bloom Filter는 "이 원소가 집합에 있는가"라는 질문 하나만 답하는 확률적 자료구조다. 1970년 Burton Bloom이 제안했고, 지금은 데이터베이스와 캐시 계층 곳곳에 들어가 있다.

필터는 0으로 채운 비트 배열 하나에서 시작한다. 원소가 들어오면 해시 함수 몇 개를 돌려 배열 안의 위치 몇 군데를 계산하고, 그 자리 비트를 1로 바꾼다. 그리고 원소는 버린다.

그래서 원소가 아무리 긴 문자열이어도 필터에는 비트 몇 개만 남는다. 대신 되돌릴 방법이 없다. 배열을 통째로 훑어도 1이 된 비트가 어떤 원소 때문인지 알 수 없으니, 무엇이 들어 있는지 열거할 수도, 넣은 원소를 꺼낼 수도 없다.

지원하는 연산도 두 개다.

| 연산            | 설명                                              |
| ------------- | ----------------------------------------------- |
| `Add(x)`      | 원소 x에 해당하는 비트들을 1로 세운다                          |
| `Contains(x)` | x가 있을 수 있는지 판정한다. false면 확실히 없고, true면 있을 수도 있다 |

삭제도, 순회도, 값 조회도 없다. 할 수 있는 것을 이렇게까지 줄인 대가로 메모리를 크게 아낀다.

## 1.2 왜 필요한가

크롤러가 같은 페이지를 두 번 긁지 않으려면 방문한 URL을 기억해야 한다. 가장 먼저 떠오르는 선택은 `map[string]struct{}`다. 정확하고 코드도 짧다.

```go
visited := make(map[string]struct{})
visited[url] = struct{}{}
if _, ok := visited[url]; ok {
    // 이미 방문함
}
```

문제는 이 map이 URL 문자열 전체를 계속 들고 있어야 한다는 것이다. 힙 사용량은 원소 수 × (URL 길이 + map 내부 오버헤드)로 늘어난다. 실제 URL은 쿼리 파라미터까지 붙으면 100자를 넘는 경우가 흔하고, 원소가 수백만 개가 되면 이 비용이 전체 메모리를 지배한다.

Bloom Filter는 "이미 방문했다"는 판정이 가끔 틀려도 되는 상황을 전제로 이 비용을 없앤다. URL 문자열을 보관하지 않고 원소당 10비트 미만만 남긴다. 오차 1%를 허용하면 원소 하나당 9.59비트로 충분하다(3.3절). 이 값이 원소 크기와 무관하게 고정이라는 점이 핵심이다. URL이 20자든 200자든 필터 크기는 같다.

절약폭이 실제로 얼마인지는 3.4절에서 실측으로 확인할 수 있다.

## 1.3 확률적 자료구조: false positive는 있고 false negative는 없다

Bloom Filter가 "확률적"인 이유는 판정이 한쪽 방향으로만 틀리기 때문이다.

| 오류 유형          | 의미               | Bloom Filter |
| -------------- | ---------------- | ------------ |
| false positive | 넣지 않은 원소를 있다고 답함 | 발생한다         |
| false negative | 넣은 원소를 없다고 답함    | 발생하지 않는다     |

`Contains`가 false를 반환하면 그 원소는 확실히 넣은 적이 없다. true를 반환하면 두 가지 경우가 섞여 있다. 실제로 넣었거나, 다른 원소들이 우연히 그 자리 비트를 전부 세워 놨거나.

이 비대칭이 Bloom Filter를 쓸 자리를 정한다. "없음"이 확실하다는 것은, 없다고 판정된 요청에 대해 뒤쪽 저장소를 조회할 필요가 없다는 뜻이다. 있다고 나온 요청만 실제 저장소로 넘겨 확인하면 되고, false positive는 헛조회 한 번으로 끝난다. 최종 판정은 뒤쪽 저장소가 내리고, 필터는 그 앞에서 트래픽을 깎는 역할만 맡는다.

반대로 필터의 true를 최종 답으로 삼아야 하는 자리에는 쓸 수 없다. 중복 결제 차단이나 권한 검사처럼 오답의 대가가 헛조회로 끝나지 않는 판정이 여기 해당한다. 뒤에서 확인해 줄 정답 소스가 없다면 Bloom Filter 단독으로는 답을 낼 수 없다.

# 2. 동작 원리

## 2.1 비트 배열과 k개의 해시 함수

구성 요소는 두 개다. m비트짜리 비트 배열 하나, 그리고 원소를 0부터 m-1 사이의 인덱스로 매핑하는 해시 함수 k개.

이후 계속 쓰는 기호를 먼저 정리한다.

| 기호 | 의미                |
| -- | ----------------- |
| m  | 비트 배열의 전체 비트 수    |
| n  | 필터에 넣을 원소 개수      |
| k  | 해시 함수 개수          |
| p  | false positive 확률 |

비트 배열은 전부 0으로 시작한다. 원소가 들어오면 k개 해시를 돌려 k개 인덱스를 얻고, 그 자리의 비트를 다룬다. `Add`와 `Contains` 모두 이 k개 인덱스를 계산하는 부분은 같고, 그 다음에 비트를 세우느냐 읽느냐만 다르다.

해시 함수를 실제로 k개 준비할 필요는 없다. 64비트 해시 하나를 계산해 하위 32비트를 h1, 상위 32비트를 h2로 삼고, `h1 + i*h2` 꼴로 k개 인덱스를 뽑아 쓰는 방법이 표준처럼 쓰인다. Kirsch-Mitzenmacher가 제안한 이중 해싱 기법으로, 독립적인 해시 k개를 쓸 때와 false positive 확률이 사실상 같다는 것이 알려져 있다. 해시 계산이 한 번으로 줄어드니 k가 커져도 조회 비용이 거의 늘지 않는다. 구현 코드는 4장에서 본다.

## 2.2 Add - 비트를 세우는 과정

`Add`는 k개 인덱스를 계산해 해당 비트를 전부 1로 만든다. 이미 1인 자리는 그대로 둔다. 실패하는 경우가 없고 반환값도 없다.

```mermaid
flowchart LR
    A["원소 x"] --> B["xxhash 64비트 해시"]
    B --> C["h1 = 하위 32비트"]
    B --> D["h2 = 상위 32비트, 홀수 보정"]
    C --> E["pos_i = h1 + i * h2 mod m"]
    D --> E
    E --> F["비트 배열의 pos_0 부터 pos_k-1 까지 1로 설정"]
```

같은 원소를 두 번 넣어도 비트 배열의 상태는 달라지지 않는다. 서로 다른 원소가 같은 비트를 공유하는 것도 정상 동작이다. m이 유한한 이상 원소가 쌓이면 겹치는 자리가 반드시 생기고, 이 공유가 false positive의 원인이자 2.4절에서 볼 삭제 불가의 원인이다.

원소가 늘어날수록 1인 비트의 비율이 올라간다. 배열이 1로 가득 차면 모든 조회가 true를 반환하므로 필터는 아무것도 걸러내지 못하는 상태가 된다. 그래서 예상 원소 수 n을 미리 잡고 m을 그에 맞춰 정해야 한다. 이 계산이 3장의 내용이다.

## 2.3 Contains - "없다"는 확실, "있다"는 아마도

`Contains`는 `Add`와 같은 방식으로 k개 인덱스를 구한 다음, 그 자리 비트를 하나씩 확인한다. 0인 자리를 하나라도 만나면 즉시 false를 반환한다.

```mermaid
flowchart TD
    A["원소 y 조회"] --> B["k개 인덱스 계산"]
    B --> C{"모든 비트가 1인가"}
    C -->|"아니오"| D["확실히 없음"]
    C -->|"예"| E["아마도 있음, false positive 가능"]
```

0을 하나라도 봤다는 것은 y를 넣은 적이 없다는 증거가 된다. y를 넣었다면 `Add`가 그 자리를 1로 세웠을 것이고, Bloom Filter에는 1을 0으로 되돌리는 연산이 없기 때문이다. 그래서 false는 항상 정확하다.

반대로 k개가 전부 1이어도 y를 넣었다는 증거는 되지 못한다. y와 무관한 다른 원소들이 그 k개 자리를 각각 세워 놨을 수 있다. 이 우연이 일어날 확률이 곧 false positive 확률 p이고, 3장에서 계산한다.

두 연산 모두 원소 수와 무관하게 해시 한 번과 비트 접근 k번으로 끝난다.

## 2.4 왜 원소를 삭제할 수 없는가

원소 x와 y가 인덱스 하나를 공유하고 있다고 하자. x를 지우겠다고 x의 k개 비트를 0으로 되돌리면, 공유하던 그 자리도 함께 0이 된다. 그 순간 `Contains(y)`가 false를 반환한다. 넣은 원소를 없다고 답한 것이니 false negative가 생겼고, "없다는 답은 확실하다"는 성질이 깨진다.

이 성질이 깨지면 Bloom Filter를 쓸 이유가 사라진다. 1.3절에서 본 것처럼 false 판정이 정확하다는 전제 위에서 뒤쪽 저장소 조회를 생략하는 것이기 때문이다.

근본 원인은 비트 하나가 담을 수 있는 정보가 "세워졌다"뿐이라는 데 있다. 몇 개의 원소가 그 자리를 세웠는지 알 방법이 없으니, 마지막 하나가 빠졌는지 판단할 수 없다. 세운 횟수를 기록하려면 비트 대신 카운터를 둬야 하는데, 그러면 메모리 구조가 달라진다. 삭제가 꼭 필요한 경우에 쓰는 변형은 7장에서 다룬다.

# 3. 파라미터 설계 (m, n, k, p)

m, n, k, p 네 값은 하나의 식으로 묶여 있어서 셋을 정하면 나머지 하나가 결정된다. 실무에서는 예상 원소 수 n과 허용할 오차 p를 입력으로 주고 m과 k를 계산하는 방향으로 쓴다. 2.1절의 기호를 이 순서로 다시 옮긴다.

| 기호 | 의미                | 이 장에서의 역할 |
| -- | ----------------- | --------- |
| n  | 필터에 넣을 원소 개수      | 입력        |
| p  | false positive 확률 | 입력        |
| m  | 비트 배열의 전체 비트 수    | 출력        |
| k  | 해시 함수 개수          | 출력        |

## 3.1 false positive 확률 공식

```math
p = \left(1 - e^{-kn/m}\right)^k
```

유도 과정은 네 단계다.

1. 해시 한 번이 특정 비트를 세우지 않을 확률은 $1 - 1/m$이다. 인덱스가 균등 분포한다고 가정한 값이다.

2. 원소 $n$개를 넣으면 비트를 세우는 시도가 총 $kn$번 일어난다. 특정 비트가 끝까지 0으로 남을 확률은 $(1 - 1/m)^{kn}$이고, $m$이 크면 $e^{-kn/m}$으로 근사된다.

3. 따라서 임의의 비트가 1일 확률은 $1 - e^{-kn/m}$이다.

4. 넣지 않은 원소를 조회하면 $k$개 자리를 확인하는데, 그 $k$개가 모두 1이면 false positive다. 확률은 $\left(1 - e^{-kn/m}\right)^k$가 된다.

마지막 단계는 k개 위치가 서로 독립이라고 가정한 근사다. 실제 값은 이보다 조금 크지만, m이 충분히 크면 차이는 무시할 수준이다.

이 식에서 p는 m과 n이 각각 얼마인지가 아니라 m/n, 즉 원소당 비트 수와 k에만 의존한다. 원소가 10배로 늘어도 m을 10배로 잡으면 오차율은 그대로다.

## 3.2 최적 m과 k 구하기

k를 늘리면 상반된 두 효과가 생긴다. 확인할 비트가 많아지니 우연히 전부 1일 확률은 낮아지지만, 원소당 세우는 비트도 많아지니 배열이 빨리 채워진다. 그래서 p를 최소로 만드는 k가 중간 어딘가에 존재한다. 위 식을 k에 대해 미분해 최솟값을 구하면 다음과 같다.

```math
k = \frac{m}{n} \ln 2
```

이 k에서 비트 배열은 정확히 절반이 1로 채워진다. 이 값을 원래 식에 대입하고 목표 p에 대해 m을 풀면 필요한 비트 수가 나온다.

```math
m = -\frac{n \ln p}{(\ln 2)^2}
```

두 식을 그대로 옮긴 코드가 [tutorials-go의 bloom-filter 예제](https://github.com/kenshin579/tutorials-go/tree/master/golang/data-structure/bloom-filter)에 있다.

```go
// OptimalM은 원소 수 n과 목표 false positive 확률 p에 대해 필요한 비트 수를 계산한다.
// p가 (0, 1) 범위를 벗어나면 유효하지 않은 값으로 간주해 기본값 0.01로 대체한다.
//
//	m = -n * ln(p) / (ln2)^2
func OptimalM(n uint64, p float64) uint64 {
	if n == 0 {
		return 1
	}
	if p <= 0 || p >= 1 {
		p = 0.01
	}
	m := -float64(n) * math.Log(p) / (math.Ln2 * math.Ln2)
	return uint64(math.Ceil(m))
}

// OptimalK는 비트 수 m과 원소 수 n에 대해 최적의 해시 함수 개수를 계산한다.
//
//	k = (m/n) * ln2
func OptimalK(m, n uint64) uint64 {
	if n == 0 {
		return 1
	}
	k := (float64(m) / float64(n)) * math.Ln2
	if k < 1 {
		return 1
	}
	return uint64(math.Round(k))
}
```

m은 올림, k는 반올림해 정수로 만든다. k는 최소 1을 보장한다. m/n이 1.44보다 작으면 계산값이 1 미만으로 떨어지는데, 해시를 0개 쓸 수는 없기 때문이다.

## 3.3 숫자로 감 잡기

원소 100만 개(n = 1,000,000)를 기준으로 목표 p를 바꿔 가며 계산한 결과다.

| 목표 p   | m (비트)   | 비트 배열 메모리 | k  | 원소당 비트 |
| ------ | -------- | --------- | -- | ------ |
| 0.1    | 4792530  | 0.57 MiB  | 3  | 4.79   |
| 0.01   | 9585059  | 1.14 MiB  | 7  | 9.59   |
| 0.001  | 14377588 | 1.71 MiB  | 10 | 14.38  |
| 0.0001 | 19170117 | 2.29 MiB  | 13 | 19.17  |

목표 FPR을 10배 낮출 때마다 원소당 약 4.8비트가 더 필요하고, 메모리는 선형으로만 늘어난다.

표의 메모리는 비트 배열(`(m+63)/64` 워드)만 계산한 값이다. 실제 힙은 Go 할당기의 사이즈 클래스 반올림 때문에 수 KB 더 크다. 그래서 3.4절의 실측 힙과 소수점 둘째 자리가 어긋날 수 있다.

## 3.4 map과의 메모리 비교

원소 100만 개를 넣었을 때 실제 힙 사용량을 잰 결과다. Bloom Filter는 p = 0.01로 잡았고, map은 키 크기를 바꿔 가며 측정했다.

| 자료구조                             | 힙 사용량      | Bloom 대비 배수 |
| -------------------------------- | ---------- | ----------- |
| Bloom Filter (p=0.01)            | 1.15 MiB   | 1배          |
| `map[uint64]struct{}` (8바이트 키)   | 36.06 MiB  | 31.2배       |
| `map[string]struct{}` (15바이트 키)  | 68.49 MiB  | 59.3배       |
| `map[string]struct{}` (54바이트 키)  | 114.29 MiB | 99.0배       |
| `map[string]struct{}` (200바이트 키) | 251.59 MiB | 217.9배      |

숫자만 보면 최대 217.9배지만, 이 배수를 그대로 인용하기 전에 알아 둘 것이 몇 가지 있다.

**배수는 키 크기가 만드는 값이다.** Bloom Filter 쪽은 원소가 무엇이든 1.15 MiB로 고정이다. 그러니 배수는 사실상 `원소 하나의 저장 비용 ÷ 원소당 비트(9.59)`이고, 표는 그 의존성을 그대로 보여준다. 우리 데이터의 키가 얼마나 큰지를 먼저 확인해야 어느 행이 자기 상황에 해당하는지 알 수 있다.

**배수는 세 가지를 포기하고 산 값이다.** `map`은 정확하고, 원소를 다시 꺼낼 수 있고, 삭제할 수 있다. Bloom Filter는 1%를 틀리고, 원소를 꺼낼 수 없고, 삭제할 수 없다. 이 교환이 받아들일 만한지는 6.5절에서 다시 짚는다.

**중간 선택지가 있다.** URL 문자열을 그대로 담는 대신 64비트 해시만 담으면 `map[uint64]struct{}`가 된다. 표의 첫 행이다. 정확도를 사실상 유지하면서 상당량을 아낄 수 있으니, Bloom Filter가 유일한 대안인 것처럼 판단하면 안 된다.

**Bloom Filter도 원소를 만들 때는 메모리를 쓴다.** 측정에서 Bloom 쪽도 URL 100만 개를 실제로 만들었고, 필터에 넣은 뒤 GC가 회수했을 뿐이다. "원소를 메모리에 올리지 않아도 된다"가 아니라 "**보관**하지 않아도 된다"가 정확한 표현이다.

**측정 방법.** `runtime.MemStats.HeapAlloc` 델타를 GC 이후에 읽어 살아 있는 객체만 쟀다. Apple M1 / Go 1.26 기준이며, Go의 map 구현이나 아키텍처가 다르면 `map` 쪽 수치는 달라진다.

# 4. Go로 직접 구현하기

2장의 원리와 3장의 공식을 그대로 코드로 옮긴다. 필요한 것은 비트 배열, 인덱스 계산, 두 개의 연산뿐이라 주석까지 합쳐도 130줄 남짓이다. 외부 의존성은 해시 함수 하나(`cespare/xxhash/v2`)다. 전체 코드는 3.2절에서 링크한 [tutorials-go의 bloom-filter 예제](https://github.com/kenshin579/tutorials-go/tree/master/golang/data-structure/bloom-filter)에 있다.

## 4.1 자료구조 정의

```go
// BloomFilter는 비트 배열 기반의 확률적 집합이다.
// Contains가 false를 반환하면 원소는 확실히 없고,
// true를 반환하면 있을 수도 있다(false positive).
//
// 동시성 안전하지 않다. 여러 goroutine에서 Add를 호출하려면
// 호출하는 쪽에서 락을 걸어야 한다.
type BloomFilter struct {
	bits []uint64 // 비트 배열을 uint64 워드 단위로 저장
	m    uint64   // 전체 비트 수
	k    uint64   // 해시 함수 개수
	n    uint64   // Add 호출 횟수
}
```

주석의 동시성 경고를 먼저 짚어 둔다. 비트 배열을 락 없이 읽고 쓰므로 여러 goroutine이 같은 필터를 쓰려면 호출하는 쪽에서 락을 걸거나 6.2절처럼 필터를 프로세스 밖에 두어야 한다. 5장의 `bits-and-blooms/bloom`도 마찬가지라 라이브러리로 바꾼다고 해결되지 않는다.

비트 배열을 `[]bool`로 두면 `bits[pos] = true` 한 줄로 끝나 코드는 더 읽기 쉽다. 문제는 Go의 `bool`이 원소당 1바이트라 정확히 8배를 낭비한다는 것이다. 3.3절의 m = 9,585,059에서 `[]bool`은 9.14 MiB, `[]uint64`는 1.14 MiB다. 원소당 9.59비트라는 1.2절의 숫자는 비트를 진짜 비트로 저장했을 때만 성립한다.

워드 배열의 길이 `(m+63)/64`는 올림 나눗셈이다. `m/64`로 두면 64로 나누어떨어지지 않는 m에서 마지막 몇 비트를 담을 자리가 사라진다. m = 100이면 워드 2개, 즉 128비트를 잡고 남는 28비트는 버린다.

필드 `n`은 이름과 달리 원소 개수가 아니라 **`Add`를 호출한 횟수**다. 필터는 원소를 저장하지 않아 중복인지 알 방법이 없으니 세는 쪽을 포기했다. 이 값은 4.5절에서 이론 FPR의 n 자리에 들어가므로, 중복 삽입이 많으면 실제보다 비관적인 추정치가 나온다.

## 4.2 파라미터로부터 필터 만들기

생성자는 두 개다. m과 k를 직접 아는 경우와, n과 p만 아는 경우다.

```go
// New는 비트 수 m과 해시 함수 개수 k를 직접 지정해 생성한다.
func New(m, k uint64) *BloomFilter {
	if m == 0 {
		m = 1
	}
	if k == 0 {
		k = 1
	}
	return &BloomFilter{
		bits: make([]uint64, (m+63)/64), // 올림 나눗셈
		m:    m,
		k:    k,
	}
}

// NewWithEstimates는 예상 원소 수 n과 목표 false positive 확률 p로부터
// m과 k를 자동 계산해 생성한다.
func NewWithEstimates(n uint64, p float64) *BloomFilter {
	m := OptimalM(n, p)
	return New(m, OptimalK(m, n))
}
```

`New`의 방어 분기 두 개는 뒤쪽 연산에서 검사를 반복하지 않으려는 것이다. m이 0이면 `pos % f.m`이 0으로 나누기가 되어 패닉이 나고, k가 0이면 세우는 비트가 없어 모든 조회가 true인 필터가 된다.

`NewWithEstimates`가 부르는 `OptimalM`과 `OptimalK`는 3.2절에서 본 그 함수들이다. 실무에서 쓰는 입구는 사실상 이쪽이고, `New`는 기존 필터와 파라미터를 맞출 때나 쓰인다.

## 4.3 해시 하나로 k개 인덱스 만들기

2.1절에서 예고한 Kirsch-Mitzenmacher 이중 해싱의 실제 코드다.

```go
// hashes는 xxhash 64비트 결과 하나를 상·하위 32비트로 쪼개
// 이중 해싱(Kirsch-Mitzenmacher)에 쓸 두 값을 만든다.
// 해시 함수를 k개 따로 두지 않아도 통계적으로 동등한 분포를 얻는다.
func (f *BloomFilter) hashes(data []byte) (uint64, uint64) {
	sum := xxhash.Sum64(data)
	h1 := sum & 0xffffffff
	h2 := (sum >> 32) | 1
	return h1, h2
}
```

xxhash를 한 번 돌려 64비트를 얻고, 하위 32비트를 h1, 상위 32비트를 h2로 쓴다. 인덱스는 `h1 + i*h2`로 만든다. 해시 계산은 입력 길이에 비례하는 유일한 비용인데 이 방식이면 k와 무관하게 한 번만 낸다.

눈에 걸리는 것은 `| 1` 한 줄이다. h2를 강제로 홀수로 만드는 이 보정은 여러 구현에 관례처럼 들어가 있고, 대개 "h2가 짝수면 도달할 수 있는 인덱스가 줄어들어 FPR이 나빠진다"고 설명된다. **이 설명은 사실이 아니다.**

**실제로 이 한 줄이 막아주는 것은 `h2 == 0` 하나뿐이다.** h2가 0이면 `h1 + i*h2`가 i와 무관하게 h1이 되어 k개 인덱스가 전부 한 자리로 겹치고, 그 원소에 한해 필터는 k=1로 동작한다.

실측으로도 확인된다. m = 9,585,059 / k = 7 / n = 100만 조건에서 보정을 빼고 h2가 0인 상황을 강제하면 FPR이 **1.0%에서 9.9%로** 무너지는데, k=1일 때의 이론값 $1 - e^{-n/m} = 0.0991$과 정확히 맞는다. h2가 0이 될 확률은 $2^{-32}$라 극히 낮지만, 막는 비용이 OR 연산 한 번이니 그대로 둘 이유가 없다.

**반면 짝수 h2 자체는 해롭지 않다.** 이유와 실측은 아래에 접어 둔다.

64비트를 알뜰하게 쪼개 쓴 대가도 하나 있다. h1과 h2가 32비트라 `pos = h1 + i*h2`는 $k(2^{32} - 1)$을 넘지 못하고, m이 $k \cdot 2^{32}$보다 커지면 비트 배열 뒷부분에는 어떤 입력으로도 도달할 수 없다. 512 MiB 이상이라 이 예제의 범위 밖이지만, 코드를 가져다 쓸 사람에게는 알려야 할 한계다.

## 4.4 Add와 Contains

인덱스를 만들 수 있으면 나머지는 짧다.

```go
// Add는 원소를 필터에 추가한다.
func (f *BloomFilter) Add(data []byte) {
	h1, h2 := f.hashes(data)
	for i := uint64(0); i < f.k; i++ {
		pos := (h1 + i*h2) % f.m
		f.bits[pos/64] |= 1 << (pos % 64)
	}
	f.n++
}

// Contains는 원소가 있을 수 있는지 확인한다.
// false면 확실히 없고, true면 있을 수도 있다.
func (f *BloomFilter) Contains(data []byte) bool {
	h1, h2 := f.hashes(data)
	for i := uint64(0); i < f.k; i++ {
		pos := (h1 + i*h2) % f.m
		if f.bits[pos/64]&(1<<(pos%64)) == 0 {
			return false
		}
	}
	return true
}
```

비트 하나를 다루는 방법은 두 함수가 같다. `pos/64`로 워드를 고르고 `pos%64`로 워드 안 위치를 고른다. `Add`는 그 자리에 OR로 1을 씌우고, `Contains`는 AND로 읽는다. 이미 1인 자리에 다시 OR을 해도 결과가 같으니 `Add`에는 실패 경로가 없다.

k개 인덱스를 슬라이스에 모아 처리하면 코드는 조금 더 정돈되지만 호출마다 할당이 하나 생긴다. 루프 안에서 계산하고 바로 쓰면 지역 변수 `pos` 하나로 끝나 힙 할당이 0이다. 조회 하나가 수십 나노초인 자료구조에서 할당 한 번은 그대로 지배적인 비용이 되므로 테스트로 못박아 둔다.

```go
addAllocs := testing.AllocsPerRun(100, func() {
	f.Add(key)
})
assert.Equal(t, 0.0, addAllocs)
```

5.2절에서 라이브러리와 나란히 놓을 때 `B/op`가 양쪽 모두 0이어야 순수한 연산 비용을 비교하는 셈이 된다.

`Contains`의 `return false`가 루프 안에 있다는 점도 봐 둘 만하다. 0인 비트를 하나라도 만나면 남은 프로브를 건너뛰고 즉시 빠져나온다. 넣지 않은 원소는 대개 첫 두어 번 안에 0을 만나니 없는 키가 있는 키보다 빨라야 자연스럽다. 실제로 그런지는 5.2.1절에서 확인한다.

## 4.5 false positive rate 실측

3.1절의 공식이 맞는지 직접 재 본다. 설계 용량만큼 채운 뒤 넣지 않은 키로만 100만 번 조회하고, 그중 몇 번이 true로 나오는지 센다.

```go
func TestBloomFilter_실측_FalsePositiveRate(t *testing.T) {
	const (
		n      = 100_000   // 설계 용량
		trials = 1_000_000 // 넣지 않은 원소로 조회할 횟수
		target = 0.01      // 목표 false positive 확률
	)

	f := NewWithEstimates(n, target)
	for i := 0; i < n; i++ {
		f.Add([]byte(fmt.Sprintf("member-%d", i)))
	}

	falsePositives := 0
	for i := 0; i < trials; i++ {
		// "member-" 접두사와 겹치지 않는 키만 조회한다
		if f.Contains([]byte(fmt.Sprintf("stranger-%d", i))) {
			falsePositives++
		}
	}

	actual := float64(falsePositives) / float64(trials)
	t.Logf("m=%d k=%d n=%d", f.Cap(), f.K(), f.Count())
	t.Logf("false positive 건수=%d/%d", falsePositives, trials)
	t.Logf("이론 FPR=%.5f 실측 FPR=%.5f", f.EstimatedFPR(), actual)

	assert.InDelta(t, target, actual, 0.001)
}
```

조회 키에 `stranger-` 접두사를 쓴 것은 넣은 키(`member-`)와 문자열이 겹칠 가능성을 없애기 위해서다. 하나라도 겹치면 그건 false positive가 아니라 진짜 positive라 집계가 오염된다.

결과는 다음과 같다.

| 항목                | 값         |
| ----------------- | --------- |
| m (비트)            | 958506    |
| k                 | 7         |
| n                 | 100,000   |
| 조회 횟수             | 1,000,000 |
| false positive 건수 | 10008     |
| 이론 FPR            | 0.01004   |
| 실측 FPR            | 0.01001   |

두 값의 차이는 0.00003, 건수로는 30건이다. 조회 100만 회는 성공 확률 0.01인 베르누이 시행 100만 번이므로 false positive 건수는 이항분포를 따르고, 표준편차는 $\sqrt{1{,}000{,}000 \times 0.01 \times 0.99} \approx 99.5$건이다. 30건 차이는 $0.3\sigma$라 반복하면 매번 이 정도로 흔들리는 것이 정상이고, 이론값이 이 범위에 들어왔다는 것은 3.1절의 근사가 실제 동작과 어긋나지 않는다는 뜻이다.

# 5. 라이브러리 활용 (bits-and-blooms/bloom)

원리를 알았으니 실무에서 쓸 물건을 본다. Go 진영에서 사실상 표준으로 쓰이는 [bits-and-blooms/bloom](https://github.com/bits-and-blooms/bloom)이다. 4장의 구현과 뼈대는 같고, 없는 것들이 붙어 있다.

## 5.1 기본 사용법

```go
func TestLibrary_기본_사용법(t *testing.T) {
	// 100만 개를 1% false positive 확률로 담는 필터
	filter := bloom.NewWithEstimates(1_000_000, 0.01)

	filter.Add([]byte("hello"))
	filter.AddString("world")

	assert.True(t, filter.Test([]byte("hello")))
	assert.True(t, filter.TestString("world"))
	assert.False(t, filter.TestString("없는-키"))

	// m은 양쪽이 항상 같다. k는 라이브러리가 올림(ceil), 직접 구현이 반올림(round)이라
	// p에 따라 1 차이가 날 수 있고, p=0.01에서는 우연히 일치한다.
	assert.Equal(t, OptimalM(1_000_000, 0.01), uint64(filter.Cap()))
	assert.Equal(t, uint(7), filter.K())
}
```

이름만 다르고 하는 일은 4장과 같다. `Add`/`Test`가 바이트 슬라이스를, `AddString`/`TestString`이 문자열을 받는다.

**m은 양쪽이 항상 같지만 k는 다를 수 있다.** m 공식은 올림 처리까지 같아서 어떤 p를 넣어도 값이 일치한다.

갈리는 것은 k를 정수로 만드는 방법이다. 라이브러리는 $k = \lceil (m/n) \ln 2 \rceil$으로 올리고, 4장 구현은 $k = \mathrm{round}((m/n) \ln 2)$로 반올림한다. 그래서 p = 0.1에서는 3과 4로, p = 0.0001에서는 13과 14로 갈린다. p = 0.01에서 둘 다 7이 나온 것은 계산값 6.64가 반올림해도 올림해도 7이 되기 때문이지 같은 규칙을 쓰기 때문이 아니다.

조회와 추가를 한 번에 처리하는 `TestAndAdd` 계열도 있다. 중복 제거에 바로 쓸 수 있는 형태다.

```go
func TestLibrary_TestAndAdd로_중복_제거(t *testing.T) {
	filter := bloom.NewWithEstimates(1000, 0.01)

	urls := []string{"a.com", "b.com", "a.com", "c.com", "b.com"}
	unique := 0
	for _, u := range urls {
		if !filter.TestAndAddString(u) {
			unique++
		}
	}

	assert.Equal(t, 3, unique)
}
```

`TestAndAddString`은 조회 결과를 반환하고 나서 비트를 세운다. false면 처음 보는 항목이니 그 자리에서 처리하고, true면 건너뛴다. 편하지만 **false positive가 나면 처음 보는 항목을 이미 본 것으로 착각해 조용히 버린다.** 빠뜨리면 안 되는 항목이 섞인 큐에는 쓸 수 없다는 뜻이고, 이 손실은 6.4절에서 다시 본다.

직접 구현에 없는 기능도 있다. 필터를 저장했다 복원하는 직렬화다.

```go
func TestLibrary_직렬화_왕복(t *testing.T) {
	original := bloom.NewWithEstimates(1000, 0.01)
	original.AddString("hello")

	var buf bytes.Buffer
	_, err := original.WriteTo(&buf)
	require.NoError(t, err)

	restored := bloom.New(1, 1) // 크기는 ReadFrom이 덮어쓴다
	_, err = restored.ReadFrom(&buf)
	require.NoError(t, err)

	assert.True(t, restored.TestString("hello"))
	assert.Equal(t, original.Cap(), restored.Cap())
	assert.Equal(t, original.K(), restored.K())
}
```

`WriteTo`와 `ReadFrom`은 `io.Writer`/`io.Reader`를 받으니 대상이 파일이든 네트워크든 상관없고, m과 k도 함께 실려 나가 복원 쪽은 크기를 몰라도 된다. 재시작마다 수백만 건을 다시 넣지 않아도 되고 배치로 만든 필터를 여러 서버에 배포할 수도 있다. 4장 구현에는 없는 기능이다.

두 구현의 정확도가 같은지도 확인해 둔다.

```go
func TestLibrary_실측FPR은_비슷하지만_오답_대상은_다르다(t *testing.T) {
	const (
		n      = 100_000
		trials = 100_000
	)

	mine := NewWithEstimates(n, 0.01)
	lib := bloom.NewWithEstimates(n, 0.01)
	for i := 0; i < n; i++ {
		key := []byte(fmt.Sprintf("member-%d", i))
		mine.Add(key)
		lib.Add(key)
	}

	var mineFP, libFP, bothFP int
	for i := 0; i < trials; i++ {
		key := []byte(fmt.Sprintf("stranger-%d", i))
		m, l := mine.Contains(key), lib.Test(key)
		if m {
			mineFP++
		}
		if l {
			libFP++
		}
		if m && l {
			bothFP++
		}
	}
	// 이하 로그 출력과 검증은 생략한다
}
```

조회 10만 회에서 **직접 구현 965건, 라이브러리 1016건, 둘 다 틀린 건 7건**이 나왔다. 앞의 두 값은 모두 목표치 1% 근처다. 정확도 면에서 두 구현은 차이가 없다.

흥미로운 것은 세 번째 값이다. 각자 1%씩 틀리는데 같은 키에서 틀리는 경우는 7건뿐이다. 해시가 다르니 어떤 키가 하필 k개 비트를 다 밟는지도 달라진다. 두 오답 집합이 독립이라면 겹칠 기대값이 $100{,}000 \times 0.01 \times 0.01 = 10$건이니 실측 7건은 그 근처다. 정확도가 같다는 말이 "같은 답을 낸다"는 뜻은 아니다.

## 5.2 직접 구현과 성능 비교

같은 조건에서 두 구현을 나란히 재 봤다. 양쪽 모두 m = 9,585,059 / k = 7이고, 설계 용량인 100만 개까지 채운 뒤 측정했다. 키는 54바이트짜리 URL이다. 필터가 비어 있으면 없는 키가 첫 프로브에서 곧바로 반환되어 실제보다 빠르게 나오므로 채운 상태로 재야 한다.

```text
BenchmarkAdd_직접구현-8                43154478   28.51 ns/op   0 B/op   0 allocs/op
BenchmarkAdd_라이브러리-8              25961148   47.05 ns/op   0 B/op   0 allocs/op
BenchmarkContains_직접구현-8           45509133   26.66 ns/op   0 B/op   0 allocs/op
BenchmarkContains_라이브러리-8         27284404   44.42 ns/op   0 B/op   0 allocs/op
BenchmarkContains_직접구현_없는키-8     51180073   22.87 ns/op   0 B/op   0 allocs/op
BenchmarkContains_라이브러리_없는키-8    23989464   51.02 ns/op   0 B/op   0 allocs/op
```

| 연산                | 직접 구현    | 라이브러리    | 배수    |
| ----------------- | -------- | -------- | ----- |
| `Add`             | 28.51 ns | 47.05 ns | 1.65배 |
| `Contains` (있는 키) | 26.66 ns | 44.42 ns | 1.67배 |
| `Contains` (없는 키) | 22.87 ns | 51.02 ns | 2.23배 |

여섯 벤치마크 모두 `0 B/op`, `0 allocs/op`다. 측정 환경은 Apple M1 / Go 1.26이다.

이 표를 "직접 만든 게 유명 라이브러리보다 낫다"로 읽으면 곤란하다. 숫자가 왜 이렇게 나왔는지 네 가지를 함께 봐야 한다.

**빨라진 원인은 알고리즘이 아니라 해시 함수 선택이다.** 비트를 세우고 읽는 부분은 양쪽이 사실상 같은 코드다. 다른 것은 앞단이다. 직접 구현은 xxhash를 한 번 돌려 64비트를 얻고 32비트씩 쪼갠다. 라이브러리는 murmur3 128비트를 두 번 돌려 256비트를 만들고, 그 결과를 `bitset` 타입을 한 겹 거쳐 쓴다. 해시만 따로 재면 54바이트 입력에서 xxhash가 14.2ns, murmur3-128이 30.0ns다. 차이의 대부분이 여기서 나온다.

**덜 만들어서 빠른 부분이 분명히 있다.** 해시 비트를 64개만 쓴 대가로 m이 $2^{32}$를 넘을 수 없어 p = 0.01 기준 약 4.5억 개가 상한이다. 4.3절에서 짚은 그 제약이 곧 여기 적힌 속도의 값이다. 라이브러리는 256비트를 쓰므로 이 한계가 없다.

**정확도를 깎아서 얻은 속도는 아니다.** 5.1절의 오답 비교가 근거다. 실측 FPR이 양쪽 다 목표치 근처였다.

**그리고 이 표로 라이브러리를 버리지는 마라.** 20ns든 50ns든, 실제 서비스에서 Bloom Filter 조회 앞뒤에 놓이는 것은 DB 조회나 네트워크 왕복이고 그쪽은 수십 마이크로초를 쓴다. 1000배 이상 큰 비용에 가려져 계측기에도 잘 잡히지 않는 차이다.

### 5.2.1 없는 키가 더 빠를 것 같지만

표에서 눈에 걸리는 곳이 하나 있다. 직접 구현은 없는 키가 있는 키보다 빠른데(26.66 → 22.87ns) 라이브러리는 오히려 느려진다(44.42 → 51.02ns). 두 구현의 격차도 있는 키에서 1.7배이던 것이 없는 키에서 2.2배로 벌어진다.

없는 키가 빨라야 한다는 기대에는 근거가 있다. 4.4절에서 본 대로 `Contains`는 0인 비트를 만나면 즉시 반환하고, 프로브 수를 세어 보면 있는 키가 평균 7.00회, 없는 키가 2.05회다. 비트 밀도 0.518에서의 이론값 2.054와 맞는다. 일은 확실히 덜 한다.

그러면 라이브러리는 왜 느려지는가. 가장 먼저 떠오르는 답은 "라이브러리가 조기 반환을 안 하는 것 아닐까"다. **틀렸다.** 소스를 열어 보면 `Test`도 첫 0비트에서 즉시 반환한다. 프로브 수를 실측해도 같은 값이 나온다. 그럴듯하지만 사실이 아닌 설명이라 짚고 넘어간다.

진짜 원인은 조기 반환이 **어디서** 일어나는지가 데이터에 따라 매번 달라진다는 데 있다. 어떤 키는 첫 프로브에서, 어떤 키는 네 번째에서 끝난다. CPU 입장에서 이 분기는 예측할 수 없고, 예측이 빗나가면 파이프라인을 비우고 다시 채워야 한다.

그리고 이 페널티의 크기는 앞단 해시가 정한다. murmur3를 쓰는 라이브러리만 크게 손해 보는 이유인데, 근거가 되는 실험은 아래에 접어 둔다.

<details>
<summary><b>분기 예측이 원인이라는 근거 — 대조 실험과 세 상태 비교</b></summary>

결정적인 증거는 대조 실험에서 나왔다. 벤치마크에 쓰는 키 1000개를 **종료 지점 순으로 정렬만** 했다. 키 집합도, 프로브 수도, 메모리 접근량도 그대로다. 바뀐 것은 분기 패턴이 규칙적으로 늘어섰다는 것뿐이다. 결과는 라이브러리 51.0 → 32.2ns였다. 같은 조작에서 직접 구현은 23.3 → 21.8ns로 거의 움직이지 않았다.

| 없는 키 조회 | 원래 순서   | 종료 지점 순 정렬 |
| ------- | ------- | ---------- |
| 직접 구현   | 23.3 ns | 21.8 ns    |
| 라이브러리   | 51.0 ns | 32.2 ns    |

이 절의 대조 실험 수치는 위 벤치마크 표와 별개로 실행한 것이라, 같은 조건이라도 소수점 아래가 조금씩 다르다(직접 구현의 없는 키가 22.87ns와 23.3ns로 갈리는 식이다). 절대값을 표끼리 맞춰 보는 대신 같은 실행 안에서의 차이를 보면 된다.

남은 질문은 왜 라이브러리만 이렇게 크게 손해를 보는가다. 답은 다시 해시 비용이다. 조기 반환을 없앤 분기 없는 변형으로 재면 양쪽 다 없는 키가 있는 키와 같은 시간이 된다(라이브러리 있는 키 44.7ns, 없는 키 44.5ns). 여기에 해시 함수를 서로 바꿔 끼우면 페널티가 해시를 따라 옮겨 간다. murmur3-128을 4장 프로빙 코드에 붙이면 없는 키 페널티가 +19.8ns로 생기고, xxhash를 라이브러리 프로빙에 붙이면 +0.8ns로 사라진다. 민감도를 정하는 것은 프로빙 코드가 아니라 앞단의 해시다.

세 가지 상태를 나란히 놓으면 계산이 맞아떨어진다. 조기 반환이 아예 없는 분기 없는 변형, 조기 반환이 있고 예측까지 되는 정렬 상태, 그리고 실제 상황인 조기 반환이 있고 예측은 안 되는 상태다.

| 없는 키 조회 | 분기 없음   | 조기 반환 + 예측 가능 | 조기 반환 + 예측 불가 (실제) |
| ------- | ------- | ------------- | ------------------ |
| 직접 구현   | 29.3 ns | 21.8 ns       | 23.3 ns            |
| 라이브러리   | 44.5 ns | 32.2 ns       | 51.0 ns            |

조기 반환이 벌어 주는 몫은 양쪽 다 적지 않다. 예측만 된다면 직접 구현은 7.5ns, 라이브러리는 12.3ns를 아낀다. 갈리는 곳은 예측이 빗나갈 때 무는 값이다. 직접 구현은 1.5ns를 물어 순이득 6ns가 남지만, 라이브러리는 18.8ns를 물어 아낀 12.3ns를 다 까먹고 6.5ns 손해로 끝난다. 벤치마크 표의 44.42 → 51.02ns가 이 손해다.

같은 조기 반환이 한쪽에서는 최적화이고 다른 쪽에서는 비용이다.

정직하게 남길 한계가 하나 있다. 방향과 원인은 위 실험으로 규명됐지만 크기까지 전부 설명되지는 않는다. 예측 가능한 경로에서 비용이 같아지도록 조건을 맞춰도 murmur3 쪽 페널티가 지연 시간 스케일링으로 예상되는 값보다 약 2.5배 크다. 분기 예측 실패 횟수를 직접 세면 확인할 수 있겠지만 macOS에서는 해당 성능 카운터에 접근할 수 없어 이 부분은 확인하지 못했다.

</details>

교훈은 하나다. 조기 반환은 공짜가 아니다. 건너뛴 일의 값보다 예측 실패의 값이 크면 손해가 된다. 반복 횟수가 적고 본체가 가벼운 루프일수록 이 역전이 일어나기 쉽다.

## 5.3 직접 구현할 때 vs 라이브러리를 쓸 때

**라이브러리가 실무 기본값이다.** 직렬화와 `Merge`, `TestAndAdd`가 붙어 있고 m 상한도 없다. 5.2절의 속도 차이는 4장 구현이 이 기능들을 포기하고 얻은 것이니, 재시작 후 필터를 다시 채우는 시간만 따져도 직렬화 하나가 20ns를 되사고 남는다.

**직접 구현이 맞는 경우도 있다.** 원리를 이해하고 싶을 때, 그리고 필터를 저장하거나 프로세스 밖으로 내보낼 일이 없고 원소 규모가 상한에 한참 못 미칠 때다. 의존성 하나를 줄이는 값어치가 있는 환경이라면 130줄을 직접 들고 가는 것도 선택지다.

# 6. 실무에서 어디에 쓰이는가

지금까지는 필터 안쪽을 봤다. 이제 바깥을 본다. 네 사례를 보는데, 무엇을 걸러내는지보다 **false positive가 났을 때 무슨 일이 벌어지는지**가 중요하다. 걸러내는 양이 아무리 커도 오답의 대가를 감당할 수 없으면 쓸 수 없는 자리다.

| 사례                | 걸러내는 것          | false positive의 대가 | 최종 판정자           |
| ----------------- | --------------- | ------------------ | ---------------- |
| 6.1 LSM 저장소       | 없는 키를 찾는 디스크 읽기 | 블록 한 번 헛읽기         | 디스크 블록           |
| 6.2 캐시 관통         | 없는 키의 캐시·DB 조회  | DB 한 번 헛조회         | DB               |
| 6.3 Safe Browsing | 목록 다운로드와 URL 노출 | 서버 왕복 한 번          | Safe Browsing 서버 |
| 6.4 크롤러 중복 제거     | 방문한 URL 재방문     | **페이지 하나 영구 유실**   | **없음**           |

마지막 열이 갈림길이다. 6.1~6.3은 뒤에서 정답을 내주는 것이 있어 오답의 대가가 헛조회 한 번으로 끝나지만, 6.4는 그 뒷단이 없어 손실이 그대로 남는다.

## 6.1 데이터베이스 - SSTable 조회 건너뛰기

Cassandra, RocksDB, LevelDB, HBase 같은 LSM 트리 기반 저장소는 쓰기를 메모리에 모았다가 SSTable이라는 불변 파일로 내려쓴다. 파일이 불변이라 갱신도 새 SSTable에 새 버전을 쌓는 식이어서, 키 하나를 찾으려면 메모리 테이블부터 최신 SSTable 순으로 내려가며 뒤져야 한다. 조회 한 번에 파일 수십 개를 여는 상황이 나온다.

여기서 각 SSTable마다 Bloom Filter를 하나씩 둔다. 필터에는 그 SSTable에 들어 있는 키가 전부 들어가 있다. 조회할 때 필터가 "없음"이라고 답하면 그 SSTable의 디스크 블록은 읽지 않고 건너뛴다.

```mermaid
flowchart TD
    A["키 조회"] --> B{"이 SSTable의 Bloom Filter"}
    B -->|"없음"| C["디스크를 읽지 않고 건너뜀"]
    B -->|"아마도 있음"| D["디스크 블록 읽기"]
    D --> E{"블록에 키가 실제로 있는가"}
    E -->|"있음"| F["값 반환"]
    E -->|"없음"| G["헛읽기"]
    C --> H["다음 SSTable로"]
    G --> H
```

조회하는 키는 대개 한 SSTable에만 있으므로 나머지 전부가 헛읽기 후보이고, 필터가 그 대부분을 쳐낸다.

3.3절의 교환은 여기서 운영 옵션으로 노출돼 있다. Cassandra는 테이블마다 `bloom_filter_fp_chance`로 목표 p를 정한다. 값을 낮추면 헛읽기가 줄지만 필터가 차지하는 메모리가 늘고, 이 메모리는 노드에 상주한다. RocksDB는 p 대신 키당 비트 수를 직접 지정하는데, 흔히 쓰는 10비트는 3.3절 표에서 p = 0.01에 필요한 원소당 비트가 9.59였던 그 숫자다.

## 6.2 캐시 관통 방어

캐시를 앞에 두는 이유는 DB에 가는 요청을 줄이기 위해서다. 그런데 **존재하지 않는 키**로 요청이 들어오면 이 구조가 무너진다. 캐시는 미스를 내고 DB는 "없음"을 반환하는데 없는 값은 캐시에 넣을 것이 없으니, 다음 요청도 똑같이 DB까지 간다. 이런 요청이 쏟아지면 캐시가 있으나 마나 한 상태로 DB가 부하를 받는다. 이걸 캐시 관통(cache penetration)이라고 부른다.

앞단에 Bloom Filter를 두면 이 경로를 끊을 수 있다. 존재하는 키 전체를 필터에 넣어 두고, 필터가 "없음"이라고 답한 요청은 캐시도 DB도 건드리지 않고 곧바로 반환한다.

```mermaid
flowchart LR
    A["요청 key"] --> B{"Bloom Filter"}
    B -->|"없음"| C["즉시 미존재 응답"]
    B -->|"아마도 있음"| D{"캐시"}
    D -->|"히트"| E["캐시 값 반환"]
    D -->|"미스"| F["DB 조회"]
    F --> G["결과 반환"]
```

Redis를 이미 쓰고 있다면 RedisBloom 모듈이 이걸 명령으로 제공한다.

```text
redis> BF.RESERVE users:exists 0.01 1000000
OK
redis> BF.ADD users:exists user:10001
(integer) 1
redis> BF.EXISTS users:exists user:10001
(integer) 1
redis> BF.EXISTS users:exists user:99999
(integer) 0
```

`BF.RESERVE`에 목표 오차율과 예상 원소 수를 주면 3.2절의 공식대로 m과 k를 잡아 준다. `BF.ADD`의 반환값 0은 5.1절의 `TestAndAdd`와 같은 의미라 "확실히 이미 있음"으로 읽으면 안 된다.

false positive가 나 봐야 필터를 안 뒀을 때의 원래 동작으로 돌아갈 뿐이라 손해는 없다. 다만 이 패턴에는 운영상 함정이 셋 붙는다.

| 함정                    | 결과                                 |
| --------------------- | ---------------------------------- |
| 쓰기 경로에서 `BF.ADD` 누락   | 존재하는 키를 "없음"으로 응답. DB를 건너뛰므로 눈에 띄지 않는다 |
| 삭제된 키를 뺄 수 없음 (2.4절)  | 지워진 키 요청이 계속 DB까지 통과. 걸러내는 힘이 시간에 따라 떨어진다 |
| 실제 키 수가 예상을 초과 (3장)   | FPR이 올라 통과율 상승. 첫 번째와 겹쳐 의미가 옅어진다  |

첫 번째는 자료구조의 false negative가 아니라 운영 실수다. 필터에 넣지 않은 원소를 없다고 답하는 것은 정상 동작이고, 쓰기와 필터 갱신은 같은 트랜잭션에 묶이지도 않는다.

세 가지 모두 결론이 같다. 이 패턴을 쓰려면 **주기적으로 전체 키 집합을 훑어 필터를 새로 만들고 통째로 교체하는 배치**가 따라붙는다. 필터를 한 번 채워 두고 잊는 구조로 설계하면 시간이 지나면서 조용히 망가진다.

## 6.3 Chrome Safe Browsing

브라우저는 사용자가 방문하려는 URL이 악성 목록에 있는지 확인해야 한다. 목록은 수백만 건이라 통째로 내려받게 할 수 없다. 그렇다고 방문할 때마다 URL을 서버에 물어볼 수도 없다. 그건 사용자의 전체 방문 기록을 서버로 보내는 것이 된다.

해법은 로컬에서 1차로 거르고 걸린 것만 서버에 확인하는 것이다. 악성이 아닌 URL은 거의 전부 로컬에서 끝나므로 서버로 나가는 요청은 극히 일부만 남는다.

다른 것은 동기다. 앞의 두 사례는 디스크 I/O와 DB 부하를 아끼려고 필터를 뒀다. 여기서 아끼는 것은 **대역폭과 프라이버시**다. 목록 전체를 내려받지 않아도 되고, 사용자가 보는 모든 URL을 서버에 넘기지 않아도 된다. 후자는 성능 문제가 아니라 설계 요건이다.

한 가지 정정할 것이 있다. Chrome이 Safe Browsing에 Bloom Filter를 썼다는 설명은 널리 인용되지만 **과거형이다.** Chromium은 2012년 9월에 로컬 판정을 Bloom Filter에서 prefix set으로 교체했다. 지금의 Safe Browsing Update API는 URL의 SHA-256 해시 프리픽스(보통 4바이트)를 내려받아 두고, 프리픽스가 걸리면 서버에 전체 해시 목록을 요청해 대조한다. 교체 이유는 Chromium 코드 리뷰에 적혀 있지 않아 추측하지 않는다.

해시 프리픽스 집합도 성질이 같아 안 걸리면 확실히 없고 걸리면 충돌일 수 있으니, 바뀐 것은 앞단 자료구조뿐이다. 가져갈 것은 "Chrome이 Bloom Filter를 쓴다"가 아니라 **앞에서 확률적으로 거르고 뒤에서 확정한다는 구성**이고, 그 구성만 성립하면 앞단이 무엇이든 된다.

## 6.4 크롤러 중복 제거

1.2절에서 시작한 예시로 돌아온다. 크롤러는 방문한 URL을 다시 큐에 넣지 않아야 하고, 그러려면 방문 기록을 들고 있어야 한다. `map[string]struct{}`가 정확하지만 URL 문자열 전체를 보관하는 비용을 낸다. Bloom Filter는 그 비용을 원소당 10비트 미만으로 바꾼다.

코드는 5.1절에서 이미 봤다. `TestAndAddString`이 false를 반환하면 처음 보는 URL이니 큐에 넣고, true면 건너뛴다.

여기서 **false positive가 나면 처음 보는 URL 하나를 영영 방문하지 않는다.**

필터가 "이미 봤다"고 하면 그게 최종 답이다. 확인하려면 방문한 URL 집합을 정확히 들고 있어야 하는데, 그걸 안 하려고 필터를 쓴 것이다.

그래서 **여기서는 손실이 실제로 발생한다.** p = 0.01로 잡고 100만 페이지를 크롤링하면 1만 페이지 정도를 놓친다는 뜻이다. 정확히는 1%가 설계 용량을 다 채웠을 때의 값이라 크롤링 전체 기간의 평균은 이보다 낮지만, 규모를 가늠하는 데는 이 숫자를 쓰면 된다.

허용 가능한지는 목적에 달렸다. 검색 인덱스를 넓게 채우는 것이라면 어차피 웹 전체를 긁을 수도 없고 놓친 페이지는 다른 링크를 타고 다시 발견되니 문제가 아닐 수 있다. 반대로 특정 사이트의 상품 페이지를 빠짐없이 수집해야 한다면 쓸 수 없다. p를 낮추면 손실이 줄지만 0이 되지는 않는다.

중간도 있다. false가 나온 URL은 확실히 처음 보는 것이니 그대로 진행하고, true가 나온 것만 정확한 집합에 다시 물으면 6.1의 구조로 돌아와 손실이 사라진다. 대신 그 집합을 어딘가에는 들고 있어야 해 1.2절의 메모리 문제가 돌아온다. 디스크나 외부 저장소로 밀어낼 수 있다면 필터는 그 느린 조회를 중복 후보에 한해서만 일어나게 만드는 역할이 된다.

## 6.5 쓰면 안 되는 경우

3.4절에서 미룬 이야기다. `map`을 버리고 Bloom Filter를 택하는 것은 정확성, 원소 조회, 삭제 세 가지를 내주고 메모리를 사는 거래다. 그 세 가지가 각각 어떤 자리를 막는지 정리한다.

| 쓸 수 없는 자리          | 이유                        | 해당 예                |
| ------------------ | ------------------------- | ------------------ |
| 정확한 답이 필요하고 뒷단이 없는 곳 | false positive가 곧 최종 답이 된다 | 잔액 조회, 권한 검사, 중복 결제 차단 |
| 원소를 다시 꺼내야 하는 곳    | 원소를 저장하지 않는다 (1.1절)       | 키 열거, 키에 딸린 값 조회   |
| 삭제가 잦은 곳           | 원소를 뺄 수 없다 (2.4절) → 7장의 변형 | 만료가 잦은 캐시 키        |
| 원소 수가 적은 곳         | `map`이 몇 MiB면 끝난다 (3.4절)  | 수만 개 규모            |
| 예상 원소 수를 모르는 곳     | m과 k를 나중에 늘릴 수 없다 (3장)    | 무한히 늘어나는 집합        |

첫 행이 6.4절과 갈리는 지점이다. 크롤러는 손실을 감수할지 판단할 여지가 있었지만 여기는 판단할 것이 없다. 네 번째 행에서 중요한 것은 3.4절 표의 배수가 아니라 절대량이다. 확률적 자료구조는 절대량이 아플 만큼 커졌을 때 꺼내는 물건이다.

마지막 행은 조용히 망가지는 경로라 따로 볼 만하다. p = 0.01로 설계한 필터(m/n = 9.59, k = 7)에 예상의 2배를 넣으면 원소당 비트가 4.79로 반토막 나고 k는 7로 고정된 채여서 실제 FPR이 약 16%까지 오른다. 목표치의 16배인데, 필터는 이 상태를 스스로 알려 주지 않는다.

완화책으로 필터가 차면 하위 필터를 덧붙이는 확장형 변형이 있고 RedisBloom도 `BF.RESERVE`의 `EXPANSION` 옵션으로 제공한다. 다만 조회할 때 하위 필터를 차례로 봐야 해 비용이 붙는다. 예상 원소 수를 제대로 잡는 것의 대체재가 아니라 잘못 잡았을 때의 안전장치다.

목록의 공통점은 하나다. **Bloom Filter는 뒤에서 정답을 내줄 무언가가 있을 때 제 역할을 한다.** 그게 없으면 필터의 true가 곧 최종 답이 되고, 그런 자리는 처음부터 필터의 자리가 아니다.

# 7. 변종과 대안

Bloom Filter가 못 하는 것 중 가장 아쉬운 것은 삭제다. 2.4절에서 왜 못 하는지는 봤고, 여기서는 그 문제를 푼 자료구조 둘을 본다. 세 번째로 보는 HyperLogLog는 이름이 나란히 거론되는 탓에 섞이기 쉽지만 애초에 다른 질문에 답하는 물건이다.

## 7.1 Counting Bloom Filter

2.4절의 문제는 비트 하나가 담는 정보가 "누군가 세웠다"뿐이라 몇 개가 세웠는지 알 수 없다는 것이었다. Counting Bloom Filter는 그걸 세는 것으로 푼다. 비트 하나 자리에 작은 카운터를 두는데 보통 4비트다.

| 연산            | 동작                     |
| ------------- | ---------------------- |
| `Add(x)`      | k개 자리의 카운터를 1씩 증가      |
| `Delete(x)`   | k개 자리의 카운터를 1씩 감소      |
| `Contains(x)` | k개 카운터가 모두 0보다 크면 true |

2.4절에서 x와 y가 인덱스 하나를 공유하면 x를 지울 때 y가 깨졌다. 카운터를 쓰면 그 자리 값이 2이고, x를 지우면 1로 내려가 `Contains(y)`가 여전히 통과한다. false negative가 생기지 않는다.

대가는 둘이다.

**메모리가 약 4배가 된다.** 3.3절의 m = 9,585,059를 4비트씩 잡으면 1.14 MiB가 4.57 MiB가 된다. 1.2절에서 Bloom Filter를 택한 이유가 메모리였다는 점을 생각하면 가볍지 않은 값이다.

**카운터가 오버플로할 수 있다.** 4비트의 최댓값은 15라, 한 자리를 세운 원소가 15개를 넘으면 포화되어 실제 개수와 어긋난다. 그대로 감소시키면 아직 남아 있는 원소를 지워 false negative가 생기고, 포화된 카운터를 고정하면 그 자리가 영영 0으로 내려가지 않아 필터가 조금씩 나빠진다. 어느 쪽도 공짜가 아니다.

4비트라는 관례에는 근거가 있다. 3.2절의 최적 k에서 카운터 하나의 기댓값이 $kn/m = \ln 2 \approx 0.69$라 대부분이 0이나 1이고 15는 분포의 한참 꼬리다. 드물다는 것이 안 일어난다는 뜻은 아니므로 처리 방침은 정해 둬야 한다.

## 7.2 Cuckoo Filter

Cuckoo Filter는 삭제 문제를 다른 방향에서 푼다. 카운터를 세는 대신 **원소의 지문(fingerprint)을 실제로 저장한다.** 지문은 원소를 해시해 얻은 몇 비트짜리 값이고, 이걸 Cuckoo 해싱으로 테이블에 넣는다.

각 원소는 후보 버킷을 둘 갖는다. 둘 중 빈 자리가 있으면 지문을 넣고, 둘 다 차 있으면 기존 지문 하나를 쫓아내 그 지문의 다른 후보 버킷으로 옮기는 연쇄가 일어난다. 쫓아낸 지문의 원래 원소가 무엇이었는지 모르는데 어떻게 상대 버킷을 아느냐는 문제는 **부분키 Cuckoo 해싱**이 푼다. 원소를 보관하지 않아도 되는 이유가 여기 있다.

<details>
<summary><b>부분키 Cuckoo 해싱 — 원소 없이 상대 버킷을 구하는 법</b></summary>

두 버킷을 이렇게 정의한다.

```text
i1 = hash(x)
i2 = i1 xor hash(fingerprint)
```

xor는 자기 역연산이라 `i2 xor hash(fingerprint) = i1`이 된다. 버킷 인덱스와 지문만 있으면 상대 버킷을 구할 수 있으므로 밀어내기 연쇄 중에 원소가 무엇이었는지 알 필요가 없다.

</details>

삭제는 해당 버킷에서 지문을 빼면 끝이다. 카운터도 필요 없고 메모리가 늘지도 않는다. 조회는 버킷 두 곳만 보므로 Bloom Filter가 k개 자리를 배열 전체에 흩어 읽는 것과 달리 메모리 접근이 두 군데로 모인다.

공간은 구간이 갈린다. 논문(Fan 외, "Cuckoo Filter: Practically Better Than Bloom", CoNEXT 2014)은 **목표 FPR이 대략 3%보다 낮을 때** Cuckoo Filter가 공간 최적화된 Bloom Filter보다 적게 쓴다고 보고한다. 3%보다 높아도 되는 경우에는 Bloom Filter가 유리하니, 목표 FPR을 먼저 정하고 골라야 한다.

대가는 셋이다.

**삽입이 실패할 수 있다.** 밀어내기 연쇄가 정해진 횟수를 넘으면 포기한다. Bloom Filter의 `Add`는 실패 경로가 없었는데(2.2절), Cuckoo Filter의 삽입은 오류를 반환할 수 있는 연산이라 호출부가 그 경우를 처리해야 한다.

**같은 원소를 반복해 넣는 데 한계가 있다.** 버킷 슬롯 수가 b면 같은 지문을 2b개까지만 담고 그 이상은 삽입 실패다. 흔히 쓰는 b = 4에서 같은 원소 8번이 한계다. Bloom Filter는 몇 번을 넣어도 비트 배열이 달라지지 않았다.

**넣은 적 없는 원소를 지우면 안 된다.** 지문이 우연히 일치하는 다른 원소의 자리를 지워 false negative가 생긴다. 삭제를 지원한다는 말은 "넣은 것만 지운다"는 전제 위에서 성립한다.

Go에서는 `seiflotfy/cuckoofilter`, `panmari/cuckoofilter` 같은 구현이 있고, RedisBloom도 `CF.ADD`, `CF.EXISTS`, `CF.DEL` 명령으로 제공한다.

## 7.3 HyperLogLog

확률적 자료구조를 검색하면 Bloom Filter와 나란히 나오는 이름이지만 푸는 문제가 다르다. Bloom Filter는 "x가 있는가"에 답하고, HyperLogLog는 **"몇 종류가 들어왔는가"**(cardinality 추정)에 답한다. 특정 원소를 넣을 수는 있어도 물어볼 수는 없다. 멤버십 판정에 쓸 수 있는 물건이 아니다.

원리는 이렇다. 원소를 해시하고 해시값의 앞쪽에 0이 몇 개 연속하는지 센다. 고유한 원소가 많이 지나갈수록 아주 긴 0 런이 한 번쯤 등장할 확률이 올라가므로, 관측된 최대 런 길이를 거꾸로 돌려 원소 종류 수를 추정한다. 관측 하나로는 분산이 커서 레지스터를 여러 개 두고 조화평균으로 합친다.

같은 원소를 몇 번 넣어도 해시값이 같아 중복은 저절로 무시된다. 저장하는 것이 레지스터 배열뿐이라 **원소 수와 거의 무관하게 크기가 고정된다.** Redis 기준 키 하나가 최대 12KB, 표준 오차 0.81%다. 원소가 1000개든 10억 개든 12KB다.

```text
redis> PFADD visitors:2026-07-31 user:1 user:2 user:3
(integer) 1
redis> PFCOUNT visitors:2026-07-31
(integer) 3
redis> PFMERGE visitors:week visitors:2026-07-30 visitors:2026-07-31
OK
```

`PFMERGE`로 여러 HyperLogLog를 합칠 수 있다는 점이 실무에서 유용하다. 일별 집계를 합쳐 주간 순 방문자를 구할 때 일별 값을 더하면 중복 방문자가 여러 번 세어지지만, `PFMERGE`는 레지스터를 합치므로 중복이 제거된 값이 나온다.

쓰는 자리는 일일 순 방문자 수, 고유 검색어 수처럼 개수만 알면 되는 집계다. 정확한 개수가 필요하면 Redis `SET`을 쓰고 원소를 전부 보관하는 비용을 낸다. 1.2절에서 `map`과 견준 것과 같은 거래다.

## 7.4 무엇을 고를까

| 자료구조                  | 답하는 질문 | 삭제    | 공간          | 언제 쓰나                 |
| --------------------- | ------ | ----- | ----------- | --------------------- |
| Bloom Filter          | 있는가    | 불가    | 기준          | 기본 선택지                |
| Counting Bloom Filter | 있는가    | 가능    | 약 4배        | 삭제가 필요하고 구현이 단순해야 할 때 |
| Cuckoo Filter         | 있는가    | 가능    | 낮은 FPR에서 유리 | 삭제가 필요하고 공간이 빠듯할 때    |
| HyperLogLog           | 몇 종류인가 | 해당 없음 | 매우 작음       | 고유 개수만 알면 될 때         |

기본은 Bloom Filter다. 4장에서 본 대로 구현이 단순하고, 5장의 라이브러리처럼 검증된 것이 어느 언어에나 있고, 실패하는 연산이 없다. 다른 것을 찾게 되는 계기는 대개 하나, 삭제다.

삭제가 필요하면 Cuckoo Filter를 먼저 본다. Counting Bloom Filter는 개념이 단순해 삭제 문제를 설명하기에는 좋지만 메모리 4배와 오버플로 처리를 떠안아야 하고, Cuckoo 논문 자체가 이를 비교 대상으로 놓고 공간과 성능 양쪽에서 낫다고 주장한다. 새로 만드는 시스템에서 고를 이유는 많지 않다.

HyperLogLog는 대안이 아니라 다른 도구다. "있는가"를 물을 필요가 없고 "몇 개인가"만 알면 되는 자리를 Bloom Filter로 풀고 있다면 그쪽이 훨씬 싸다.

# 8. FAQ

## 8.1 false positive 확률 공식은 어떻게 나온 건가요?

확률 도구 세 개면 3.1절의 유도를 그대로 따라갈 수 있다.

**1. 여사건: 안 일어날 확률**

어떤 일이 일어나지 않을 확률은 1에서 일어날 확률을 뺀 값이다.

```math
P(A^c) = 1 - P(A)
```

주사위에서 1이 나올 확률이 $1/6$이면, 안 나올 확률은 $1-1/6=5/6$이다.

3.1절 1단계가 이것이다. 비트가 $m$개이고 해시가 균등하게 하나를 고르면 특정 비트를 고를 확률은 $1/m$, 안 고를 확률은 $1-1/m$이다.

**2. 독립 사건의 곱: 여러 번 연달아**

서로 영향을 주지 않는 사건이면 확률을 곱한다. 같은 시행을 $N$번 반복하면 $N$제곱이 된다.

```math
P(A \cap B) = P(A) \times P(B)
```

동전을 세 번 던져 전부 앞면일 확률은 $(1/2)^3 = 1/8$이다.

3.1절 2단계다. 원소 $n$개가 각각 해시 $k$개를 쓰니 비트를 세우는 시도가 총 $kn$번이고, 그 $kn$번이 전부 특정 비트를 비껴갈 확률, 곧 **그 비트가 0으로 남을 확률**은 다음과 같다.

```math
\left(1 - \frac{1}{m}\right)^{kn}
```

**3. 지수 근사**

위 식을 그대로 두면 $m$이 밑에, $kn$이 지수에 따로 남아 파라미터 사이의 관계가 보이지 않는다. 3.2절처럼 k에 대해 미분해 최적값을 구하기도 어렵다. 지수함수로 바꾸면 m, n, k가 $kn/m$ 하나로 묶여 관계가 드러나고, 미분도 깔끔한 식으로 떨어진다. 근거는 이 극한 하나다.

```math
\lim_{m \to \infty} \left(1 - \frac{1}{m}\right)^m = \frac{1}{e} \approx 0.3679
```

극한이라고 적었지만 수렴이 빨라서 $m$이 100만이면 이미 0.36788이다. Bloom Filter가 다루는 $m$은 그보다 크므로 이 근사로 생기는 오차는 무시해도 된다.

```math
\left(1 - \frac{1}{m}\right)^{kn} = \left[\left(1 - \frac{1}{m}\right)^{m}\right]^{kn/m} \approx e^{-kn/m}
```

지수 자리에 있던 $kn$이 $kn/m$으로 압축된 것이 전부다. 이 순간부터 $m$과 $n$이 따로 놀지 않고 $kn/m$이라는 덩어리로만 등장하고, 3.1절 끝의 "p는 원소당 비트 수와 k에만 의존한다"가 여기서 나온다.

**조립**

앞의 두 도구를 한 번씩 더 쓰면 끝난다. 1번은 2·3단계에서 이미 구한 값이다.

1. 특정 비트가 0으로 남을 확률: $e^{-kn/m}$
2. 특정 비트가 1일 확률 (여사건): $1-e^{-kn/m}$
3. 그런 자리 $k$개가 전부 1일 확률 (곱): $(1-e^{-kn/m})^k$

마지막 줄이 곧 p이고, 3.1절의 공식이다.

**숫자로 검산**

3.3절의 값(m = 9,585,059 / n = 100만 / k = 7)을 넣어 본다.

| 계산                    | 의미            | 값       |
| --------------------- | ------------- | ------- |
| 7,000,000 / 9,585,059 | 지수부 $kn/m$    | 0.7303  |
| $e^{-0.7303}$         | 비트가 0일 확률     | 0.4818  |
| $1-0.4818$            | 비트가 1일 확률     | 0.5182  |
| $0.5182^7$            | $k$자리가 전부 1   | 0.01003 |

마지막 값이 4.5절의 이론 FPR 0.01004다. 그리고 중간의 0.5182는 5.2.1절의 비트 밀도 0.518과 같은 수다. 따로 잰 값이 아니라 이 유도의 3단계다.

## 8.2 최적 k에서 비트 배열이 정확히 절반 채워지는 이유는 뭔가요?

3.2절의 최적 k를 위 유도에 대입하면 바로 나온다. $k = (m/n)\ln 2$이므로 지수부 $kn/m$이 $\ln 2$가 되고,

```math
e^{-\ln 2} = \frac{1}{2}
```

이므로 비트가 1일 확률은 여사건인 $1-1/2$, 정확히 0.5다. 최적 k 식에 $\ln 2$가 등장한 것은 우연이 아니라 지수부를 $\ln 2$로 맞춰 비트 밀도를 절반으로 만드는 값이기 때문이다.

5.2.1절의 실제 밀도가 0.5가 아니라 0.518인 것은 k를 정수로 반올림했기 때문이다. 이론 최적값은 6.64인데 실제로는 7을 쓰므로 지수부가 $\ln 2 = 0.693$이 아니라 0.730이 되고, 그만큼 비트가 더 채워진다.

# 9. 마무리

긴 글이었으니 남길 것만 남긴다. 세 가지다.

**false negative가 없다는 비대칭이 쓸 자리를 정한다.** "없음"이 확실하니 없다고 판정된 요청은 뒤쪽 저장소 조회를 통째로 생략할 수 있고, 뒤집으면 뒤에서 확인해 줄 정답 소스가 있는 자리에 맞는다는 뜻이다. 6장의 사례가 전부 그 구조였고 크롤러(6.4절)만 그 소스가 없었다. 손실을 감수하겠다는 결정은 도입 시점에 내려 둬야 한다. 나중에 알게 되면 이미 놓친 페이지는 되찾을 수 없다.

**m과 k는 감이 아니라 공식으로 정한다.** 예상 원소 수 n과 허용 오차 p를 정하면 `m = -n * ln(p) / (ln2)^2`와 `k = (m/n) * ln2`가 나머지를 결정한다. 예상 원소 수를 모르면 이 자료구조를 쓰기 어렵다는 뜻이기도 하다. n을 잘못 잡은 필터는 조용히 걸러내는 힘을 잃고 스스로 그 사실을 알려 주지 않는다.

**실무에서는 라이브러리를 쓰되 파라미터의 의미는 알고 쓴다.** 직접 구현은 원리를 이해하는 데 쓰고, 운영에는 직렬화와 여유 있는 상한이 붙은 라이브러리를 쓴다. 4장의 130줄이 더 빨랐지만 그 속도는 기능과 규모 상한을 내주고 산 값이었다.

이 글에서 실측으로 바로잡은 것이 둘 있다. `h2 |= 1` 홀수 보정이 막아 주는 것은 짝수가 아니라 `h2 == 0`이고(4.3절), 없는 키 조회에서 라이브러리가 느려지는 것은 조기 반환을 안 해서가 아니라 그 분기가 예측되지 않기 때문이다(5.2.1절). 둘 다 그럴듯하고 널리 인용되는 설명이었는데 재 보니 달랐다. 널리 쓰이는 설명이라도 직접 재 보면 다를 수 있다.
