# Chronos-go로 배우는 분산 태스크 큐 — 블로그 시리즈 설계

- 작성일: 2026-07-18
- 대상 블로그: `blog-v2.advenoh.pe.kr`
- 소재 저장소: `chronos-go` (`github.com/kenshin579/chronos-go`)

## 배경과 목적

`chronos-go`는 AI 도움을 받아 개발한 Redis 기반 분산 태스크 큐/스케줄러 라이브러리다.
기능은 다양하게 구현되어 있고 테스트도 통과하지만, **내부 아키텍처와 구현이 실제로 어떻게 동작하는지
deep하게는 파악되지 않은 상태**다. 이 시리즈의 목적은 두 가지다.

1. **스터디**: 시리즈를 쓰는 과정에서 각 서브시스템의 코드를 직접 읽고 동작 원리를 정리해,
   구현을 깊이 이해한다. 글쓰기 자체가 스터디 수단이다.
2. **공유**: 분산 태스크 큐가 풀어야 하는 일반적인 설계 문제를 다루는 글로 만들어,
   독자 유입과 오픈소스 프로젝트 홍보 효과도 함께 얻는다.

## 시리즈 정체성 (혼합형)

각 편의 **제목과 도입은 일반 원리**(예: "지연 작업은 어떻게 정확한 시각에 실행되나")로 잡되,
**본문은 chronos-go의 실제 구현 해부**로 진행한다. 일반 문제를 향한 제목으로 독자층을 넓히면서,
스터디 깊이는 실제 코드로 확보한다.

## 시리즈 구성 결정

| 항목 | 결정 |
|------|------|
| 편 수 | 9편 (표준형) |
| 본문 스타일 | 개념/다이어그램 중심 + 핵심 코드 발췌 (Lua 스크립트 등) |
| 언어 | 한글만 (영문판은 반응 보고 추후 일괄 검토) |
| 목차 배열 | "태스크의 일생" 데이터 흐름 축 + 각 편은 독립 문제로 제목화 |
| 다이어그램 | mermaid (blog-v2가 `mermaid-renderer.tsx`로 렌더링 지원 확인됨) |

## 목차 (9편)

배치 논리: 1편이 전체 지도를 그리고, 2~5편이 태스크의 일생(투입→지연→실패→복구),
6~8편이 그 위의 제어 계층(우선순위→스케줄→오케스트레이션), 9편이 시리즈 전체를 관통하는
설계 제약(클러스터 안전성)으로 마무리한다. 9편은 앞선 편들에서 "왜 이 키에 해시 태그가 붙지?"라고
남겨둔 궁금증을 회수하는 편이라 마지막에 배치했다.

| # | 제목(안) | 다루는 문제 | 핵심 소재 |
|---|---------|-----------|----------|
| 1 | 분산 태스크 큐, 직접 만들면 뭐가 필요할까 — chronos-go 전체 아키텍처 | 태스크 큐가 풀어야 할 문제 지도 | 전체 컴포넌트 지도(Stream/ZSET/forwarder/recoverer/scheduler), `internal/base` 키 레이아웃, 기존 asynq 소개 글과 연결 |
| 2 | 메시지를 잃지 않고 워커에 분배하기 — Redis Stream 기반 즉시 큐 | LPUSH/BRPOP가 아닌 Stream을 쓰는 이유 | consumer group, `XREADGROUP`/`XACK`/`XDEL`, COUNT 배칭 + 파이프라이닝 |
| 3 | 지연 작업은 어떻게 정확한 시각에 실행되나 — ZSET과 forwarder | 시간 기반 작업의 저장과 승격 | delayed ZSET, `internal/rdb/forward.go` Lua, 폴링 주기 트레이드오프 |
| 4 | 실패한 작업은 어디로 가나 — 재시도, DLQ, 그리고 청소부 | 실패 격리와 메모리 바운딩 | retry 정책/backoff, archived(DLQ), lasterr, janitor |
| 5 | 워커가 죽으면 작업은 어떻게 되나 — at-least-once의 실체 | 크래시 복구와 중복 실행 | recoverer(`XAUTOCLAIM`), heartbeat(`XCLAIM ... JUSTID`), attempt 카운트, 멱등성 |
| 6 | 여러 큐를 공정하게 소비하기 — smooth weighted round-robin | 큐 우선순위와 기아 방지 | `wrr.go`, StrictPriority, 큐 pause |
| 7 | 분산 환경에서 cron을 딱 한 번만 실행하기 — 리더 선출 | split-brain과 중복 enqueue 방지 | `SET NX PX` 락, pub/sub resignation, `<schedule>:<trigger-unix>` dedup 키 |
| 8 | 태스크 오케스트레이션 — chain과 group의 완료 판정 | 순차/병렬 조합과 결과 전달 | chain/group 완료 카운팅 Lua, `PrevResult`/`GroupResults`, 1단계 중첩 제약 |
| 9 | 멀티 키 연산을 Redis Cluster에서 안전하게 — 해시 태그와 Lua 원자성 | 클러스터 안전성이라는 설계 제약 | `{queue}` 해시 태그, 글로벌 키의 단일 키 원칙, unique lock, Lua vs 트랜잭션 |

## 각 편의 공통 구조

각 편은 동일한 뼈대를 따른다.

1. **도입** — 이 편이 다루는 일반 문제 제기 + 시리즈 전체 지도에서 현재 위치를 표시한
   미니 mermaid 다이어그램. (각 편의 독립성을 확보해 어느 편부터 읽어도 되게 한다.)
2. **원리** — Redis 자료구조/명령 수준에서 동작 원리 설명. mermaid sequence/flow 다이어그램 중심.
3. **구현 해부** — chronos-go 핵심 코드 발췌 2~4개(주로 `internal/rdb`의 Lua 스크립트)와 해설.
   발췌 기준 커밋/버전을 글에 명시해, 이후 코드가 바뀌어도 글의 유효 범위가 분명하게 한다.
4. **정리** — 핵심 요약 + 다음 편 예고.

## 파일 규칙

기존 blog-v2 관행을 따른다.

- **초안 위치**: `docs/read/chronos-go-{N}-{슬러그}/index.md`
  (예: `docs/read/chronos-go-1-전체-아키텍처/index.md`)
  - `docs/read`는 이미 blog-v2의 초안 스테이징 영역이다(concurrency 6~10편, generics 4~5편 등이 대기 중).
- **최종 이전**: 각 편 완성·리뷰 후 사용자가 결정하는 시점에 `contents/go/`로 이동한다.
- **프론트매터**: 기존 시리즈 글과 동일 포맷. `series: "Chronos-go로 배우는 분산 태스크 큐"`,
  그리고 `title` / `description` / `date` / `update` / `tags`.
- **cover 이미지**: 1편만 필수(`cover.png`), 나머지 편은 선택.
- 인코딩은 UTF-8 (한글 콘텐츠 필수).

## 작성 워크플로우

한 편 단위로 다음을 반복한다. **한 번에 한 편씩만** 진행해 스터디 호흡을 유지한다.

1. **코드 스터디** — 해당 서브시스템의 chronos-go 코드를 읽고 동작을 정리해 사용자에게 공유한다.
   (이 단계가 스터디의 핵심이며, 오해나 미파악 지점을 여기서 먼저 걸러낸다.)
2. **초안 작성** — `docs/read/chronos-go-{N}-{슬러그}/index.md`에 초안을 쓴다.
3. **리뷰/수정** — 사용자 리뷰를 받고 수정한다.
4. **최종화(선택 시점)** — 사용자가 결정하면 `contents/go/`로 이동하고,
   `npm run check` + 빌드 확인 후 feature 브랜치로 PR을 생성한다.

## 비목표 (YAGNI)

- **영문판**: 이번 범위에서 제외. 한글 시리즈 완주 후 반응을 보고 별도 결정.
- **미니 재현 예제(별도 실습 코드 제작)**: 기본 스타일에서 제외. 특정 편(예: 리더 선출)에서
  이해에 크게 도움이 될 때만 부분적으로 도입.
- **contrib(prometheus/webui), 벤치마크 심층 분석**: 핵심 9편에는 넣지 않는다.
  소재가 남으면 추후 번외편으로 검토.

## 열린 항목

- 각 편의 최종 제목/슬러그는 초안 작성 시점에 확정한다(위 표는 작업 제목).
- `contents/go/`로의 이전 시점과 PR 단위(편별 vs 묶음)는 최종화 단계에서 사용자와 정한다.
