## 1. 목적

ROSCon 2026 1일차 balena 스폰서 드롭인 세션("Scaling ROS Deployments in Production with Secure OTA Updates Using balena")을
듣고 공부한 내용을 블로그 글 한 편으로 옮긴다. 시리즈로 나누지 않는다.

뼈대는 발표 자료의 balena 파트이고, 발표에서 짧게 지나간 부분을 스터디 노트로 보강한다.
현장에 깔린 ROS 2 로봇을 원격으로 업데이트할 때 생기는 문제를 balena가 어떤 구조로 푸는지를
컨테이너·Kubernetes에 익숙한 개발자 시각으로 정리하는 것이 글의 목적이다.

### 보강 절 상세

- **5절**은 발표 자료에 없던 절이다. balena 설계의 핵심이 "명령이 아니라 목표 상태를 내려보낸다"는 점이라
  따로 한 절을 둔다. 비교는 노트 4.2의 일반론(끊겨도 괜찮음, 멱등, 디바이스별 계산)으로만 쓴다.
- **11절**은 balena를 쓰지 않는 독자에게도 OTA 설계 확인 목록으로 쓸모가 있어서 넣는다. 노트 15장 표에서
  범위 밖 주제(Secure Boot, NVIDIA runtime, 다른 제품)에 기댄 행은 빼거나 balena 기본 기능 기준으로 고친다.

## 4. 작성 방침

**사내 정보는 쓰지 않는다.** 발표 자료 중 회사 내부 시스템을 다룬 슬라이드(34~36)는 통째로 뺀다.
회사 시스템·제품·저장소·로봇 이름과 이력은 경험담 형식으로도 넣지 않는다. 발표 자료 슬라이드 노트에 섞인
사내 언급도 옮기지 않는다. Obsidian 내부 링크(`[[...]]`)는 모두 지운다.

**추측해서 쓰지 않는다.** 노트에 출처와 함께 정리된 사실만 옮기고, 노트가 `[추정]`·`[미확인]`·`[불일치]`로
표시한 내용은 공식 문서나 코드로 확인된 경우에만 넣는다. 확인되지 않으면 뺀다. 이번 글 범위에 걸리는 항목은 8절에 정리했다.

- **시점을 밝힌다.** 1절에 조사 기준일을 쓰고, 버전·상태가 바뀔 수 있는 내용(experimental repo 등)에는 "2026-10 기준"을 붙인다.
- **표는 살린다.** 노트와 발표 자료의 비교표는 표로 두고, 앞뒤에 연결 문단을 1~2문장 둔다.
- **Mermaid만 쓴다.** 발표 자료의 도식은 Mermaid로 다시 그린다. 노드 텍스트에 `<br/>`를 쓰지 않는다
  (노트의 다이어그램은 모두 `<br/>`를 쓰므로 그대로 옮기지 않고 고친다). 쓸 곳은 3절 시퀀스, 4절 A/B 전환,
  5절 fleet·릴리스 관계와 reconcile 루프, 7절 업데이트 전략 gantt, 8절 단계적 배포 흐름, 9절 연결 구조다.
- **이미지는 싣지 않는다.** 세션 슬라이드 사진과 발표 자료 캡처는 쓰지 않는다.
- **compose 예시에서 범위 밖 항목을 뺀다.** `runtime: nvidia`, `io.balena.features.argus-socket`처럼 GPU 절에 기대는 줄은 지운다.
- **내부 링크는 걸지 않는다.** 연결할 만한 ROS 2 입문 시리즈는 아직 발행 전이다.
- **예시 이름은 일반화한다.** fleet slug는 노트처럼 `myorg/ros2-study`를 쓴다.
