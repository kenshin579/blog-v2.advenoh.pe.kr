# generate-quiz skill 설계

- 작성일: 2026-08-13
- 대상 저장소: `blog-v2.advenoh.pe.kr`

## 1. 목표

블로그 글에 퀴즈 세트를 추가하는 작업을 skill로 고정한다. 지금은 작성 규칙이 CLAUDE.md에 흩어져 있고 검증은 매번 임시 스크립트로 하고 있어, 같은 결함이 반복해서 나온다.

## 2. 현재 상태

- 퀴즈가 있는 글은 8편이다 (한국어 8 / 영문 7). `contents/go/go-시간-의존-코드-테스트하기`만 영문판이 없다.
- 8편 모두 **글당 quiz 블록 1개**이고, 위치도 예외 없이 **본문 마지막 장 다음, 마무리·FAQ·참고 앞**의 독립 H1 장(`# N. 퀴즈`)이다. CLAUDE.md에는 "블록을 글 중간에 여러 개 둘 수 있다"고 적혀 있지만 그렇게 쓴 글은 없다.
- CLAUDE.md에 퀴즈 절이 37줄 있다(커밋 `a79fe54`). 형식 규칙, 품질 규칙, 정답 노출 주의, 작성 후 확인. 매 세션 컨텍스트에 로드된다.
- 검증 로직은 `lib/quiz.ts`에 있다. `parseQuiz`가 YAML을 파싱하고 `isValidQuestion`이 문항을 검사하며, 형식에 안 맞는 문항은 콘솔 경고만 남기고 **조용히 버린다**.
- 사후 검수 커밋이 이미 세 번 있었다: `7ce565b`(RSS 정답 노출), `7289e77`·`71de075`(정답 위치 쏠림).
- 정답 노출은 5편 작업에서 4편에 나온 결함이다. 퀴즈 UI가 한 세트의 전 문항을 한 화면에 동시에 렌더하는데 작성자는 문항을 하나씩 쓰기 때문에 눈으로 잘 안 잡힌다.

## 3. 범위

### 포함

- 글 하나를 받아 한국어 퀴즈 세트를 작성하고 본문에 배치
- `index_en.md`가 있으면 같은 문항 수·유형·정답 인덱스로 영문 세트까지 작성
- 작성 후 스크립트 검증
- CLAUDE.md의 상세 규칙을 skill로 이관하고 포인터만 남김

### 제외 (YAGNI)

- **기존 퀴즈 검수 모드.** 이미 퀴즈가 있는 글을 훑어 고치는 것은 이 skill의 일이 아니다. `npm run check:quiz`가 전체를 훑을 수 있으므로 검출은 되고, 수정은 사람이 판단한다.
- **영문판 생성.** `index_en.md`가 없으면 한국어만 작성하고 보고한다. 글 전체 번역은 `translate-article-en`의 일이다.
- **배치 처리.** 한 번에 한 편만 다룬다.
- **빌드 파이프라인 연동.** `npm run check:quiz`를 수동으로 돌린다. 정답 쏠림 같은 항목이 빌드 실패 사유인지 판단할 근거가 아직 없다.
- **코드 스니펫 컴파일 검사.** 스크립트가 판단할 수 없어 skill 절차의 수동 확인 항목으로 남긴다.

## 4. 선택한 접근: SKILL.md(절차) + references(규칙) + 프로젝트 스크립트(검증)

규칙 문서를 `references/`로 분리한다. `content-heading-style`이 쓰는 패턴이다.

- SKILL.md는 "무엇을 어떤 순서로"만 담는다. 실제 작업에 필요했던 건 절차 9단계 정도였고 나머지는 "쓸 때 참고할 규칙"이었다.
- 규칙은 앞으로도 계속 늘어날 자산이다(사고 사례가 쌓이는 중). 절차와 분리해 두는 편이 관리하기 좋다.
- 검증 스크립트는 skill 자산이 아니라 **프로젝트 스크립트**로 둔다. `lib/quiz.ts`를 import해야 렌더러와 검증기가 갈라지지 않는다. skill 안에 별도 파서를 복제하면 `lib/quiz.ts`가 바뀔 때 조용히 어긋난다.

## 5. 산출물

| 파일 | 내용 |
|------|------|
| `.claude/skills/generate-quiz/SKILL.md` | 절차 (~130줄) |
| `.claude/skills/generate-quiz/references/quiz-rules.md` | 형식 규칙 + 품질 규칙 + 정답 노출 사례집 (~120줄) |
| `scripts/check-quiz.ts` | 검증 스크립트 (신규) |
| `package.json` | `"check:quiz": "tsx scripts/check-quiz.ts"` 추가 |
| `CLAUDE.md` | 퀴즈 절 37줄 → 4줄 포인터 |

skill 이름은 `generate-quiz`다. `generate-blog-image`, `generate-slides`와 같은 계열이다.

frontmatter의 `description`은 기존 skill들처럼 영어로 쓴다: `Use when adding an interactive quiz section to a blog article (contents/{category}/{slug}/index.md), and mirroring it into the English counterpart index_en.md`

## 6. skill 절차

1. **대상 확인** — slug(`go/go-fx-의존성-주입`) 또는 `index.md` 경로. 한 번에 한 편만. 이미 quiz 블록이 있으면 덮어쓰기 전 사용자 확인
2. **글 정독 + 근거 수집** — 절별로 문항 후보를 뽑되, 본문에 근거가 없는 것은 배제한다. 일반적으로 맞는 사실이어도 그 글에 없으면 쓰지 않는다
3. **세트 설계** — 10문항, mcq 4 / ox 2 / code 2 / blank 2. 유형 순서를 기계적으로 반복하지 않고, mcq 정답 인덱스를 0~3에 고르게 배치. blank 정답은 흔한 토큰(`any`, `struct`, `after` 등) 배제
4. **배치 위치 결정** — 본문 마지막 장 다음, 마무리·FAQ·참고 앞에 `# N. 퀴즈` H1 신설. 뒤 장 번호를 밀고 `content-heading-style` 규칙 적용
5. **밀린 장 번호 참조 확인** — 본문에 그 번호를 가리키는 문장이 없는지 확인한다. 한국어판과 영문판의 섹션 번호가 다를 수 있으니 파일별로 본다
6. **작성 및 저장** — UTF-8 확인
7. **검증** — `npm run check:quiz -- <대상>`. 에러가 0이 될 때까지 수정
8. **영문판** — `index_en.md`가 있으면 같은 문항 수·유형·정답 인덱스로 작성 후 재검증. 없으면 "영문판 없음, `translate-article-en` 필요"를 보고하고 종료
9. **보고** — 문항 표(유형·근거 절·정답)와 검사 결과

## 7. 배치 규칙 (고정)

- 글당 quiz 블록 **1개**. 렌더러는 여러 개를 지원하고 세트마다 점수가 따로 나지만, 관례는 1개다
- 위치는 본문 마지막 장 다음, 마무리·정리·FAQ·참고 앞
- 독립 H1 장으로 만들고 제목은 `# N. 퀴즈`
- 도입 문장을 한 줄 붙인다 (예: "여기까지 읽었으면 풀 수 있는 문제들이다. 답을 고르면 바로 해설이 나온다.")

## 8. `scripts/check-quiz.ts`

```bash
npm run check:quiz                          # contents/ 전체
npm run check:quiz -- go/go-fx-의존성-주입   # 특정 글만
```

인자는 slug(`go/go-fx-의존성-주입`) 또는 `index.md` 경로를 받는다. 인자가 없으면 `contents/` 아래 quiz 블록이 있는 글을 전부 검사한다. 한 글의 `index.md`와 `index_en.md`는 한 쌍으로 묶어 검사한다.

`lib/quiz.ts`에서 `parseQuiz`와 `normalizeBlankAnswer`를 import한다. 정답 노출 검사가 실제 채점과 똑같은 정규화(공백 제거 + 소문자화)를 쓰게 하기 위함이다. 검사기가 따로 정규화를 구현하면 "지문의 `after`가 허용 답 `After`와 매칭된" 사고를 다시 놓친다.

`isValidQuestion`은 export되어 있지 않다. 버려진 문항은 `yaml`의 `parse`로 얻은 원본 배열 길이와 `parseQuiz` 결과 길이를 비교해 검출한다. `lib/quiz.ts`는 수정하지 않는다.

### 에러 (exit 1)

1. YAML 파싱 실패 — 블록 전체가 코드 블록으로 노출된다
2. 파서가 조용히 버리는 문항 — 원본 배열 길이 ≠ `parseQuiz` 결과 길이
3. `blank` 문항의 `q`에 `___` 없음
4. `blank` 정답이 세트 내 **다른** 문항의 `q`·`choices`·`code`에 등장 (정답 노출)
5. `blank` 정답이 자기 문항 `q`에 등장
6. 한/영 문항 수·유형 순서·정답 인덱스 불일치 — `index_en.md`가 없으면 이 검사는 건너뛴다 (에러 아님)
7. 닫는 quiz 펜스가 빠짐 — 여는 펜스 수와 뽑힌 블록 수가 다를 때
8. 인자로 지목한 대상에 quiz 블록이 하나도 없음 (인자 없는 전체 스캔에서는 조용히 건너뛴다)

`explain`은 그 문항을 푼 뒤에만 보이므로 4번 검사 대상에 넣지 않는다.

**7·8번은 구현 중 코드 품질 리뷰에서 추가됐다.** 둘 다 "검출 실패를 통과로 보고"하는 유형이다. 7번이 없으면 펜스를 열고 안 닫았을 때 블록이 아예 안 잡혀 `에러 0`으로 통과하는데, 그건 하필 1번이 잡으려는 실패 모드다. 8번이 없으면 skill 절차의 "에러 0이 될 때까지 고친다"가 무의미해진다 — 펜스를 잘못 쓴 채 "검증 통과"로 끝난다.

### 경고 (exit 0, 리포트만)

1. 정답 인덱스 쏠림 — 인덱스로 답하는 문항(mcq+code)을 **한 묶음**으로 보고 한 값이 절반을 넘으면 발화한다. **유형별로 쪼개면 안 된다** — 10문항 4유형 구성에서 유형당 2~4문항이라, 고르게 배치해도 절반 초과가 자주 나온다(공정 배치에서의 오경보율이 n=3일 때 62%). 실제로 유형별 기준으로는 `golang-concurrency-2`의 mcq `[1,3,1]` + code `[4,2,4]`가 경고를 받는데, 합치면 `[1,1,2,3,4,4]`로 완벽히 고르다
2. **정답 보기만 유독 김** — `max/min > 1.6`이고 정답이 유일한 최장 보기일 때. 절대 글자 수를 쓰면 안 된다. 같은 내용의 영문 보기가 한국어보다 편차가 2배쯤 커서 경고가 영문판에 쏠린다. 비율은 언어 중립이다(같은 문항에서 ko 1.93 vs en 1.85). 정답이 최장일 때로 좁히는 것은 CLAUDE.md의 결함 정의("정답만 설명형으로 길면 길이만으로 정답이 티 난다")에 맞춘 것이다
3. `mcq`가 4지선다가 아님
4. `explain`에 절 참조 없음 — 저장소에 실제로 쓰이는 표기를 모두 인정한다. 한국어는 `(2.2)`, `(2.2절)`, `(7장)`, `(3장, 4.1절)`, 영문은 `(2.2)`, `(Section 7.1)`, `(Sections 3, 4.1)`. **처음에는 `(N.M)` 하나만 인식했는데 기존 글에서 경고 73건 중 61건이 이 항목이었다.** 관례를 못 따라가는 경고는 노이즈가 되어 저자가 경고 전체를 무시하게 만든다
5. 세트 문항 수가 10이 아님

### 진단 코드

에러는 `E1`~`E8`, 경고는 `W1`~`W5`로 출력한다. 위 목록의 번호와 같다. 출력에 코드를 찍으므로 검증이 `grep -q "E4"` 형태로 정확해진다.

### 출력

글별로 에러·경고를 나열하고 마지막에 요약한다. 에러가 하나라도 있으면 exit 1.

## 9. CLAUDE.md 변경

퀴즈 절을 다음으로 대체한다.

> ### 퀴즈 (선택)
>
> 글에 인터랙티브 퀴즈를 넣으려면 본문에 ` ```quiz ` 코드펜스를 열고 YAML로 문항을 적는다. 표본: `contents/go/go-fx-의존성-주입/index.md`의 5장.
>
> **퀴즈를 새로 쓰거나 고칠 때는 `generate-quiz` skill을 쓴다.** 형식·품질 규칙과 정답 노출 사례는 `.claude/skills/generate-quiz/references/quiz-rules.md`에, 검증은 `npm run check:quiz`에 있다.

기존 37줄의 내용은 전부 `references/quiz-rules.md`로 옮긴다. 유실되는 규칙이 없어야 한다.

## 10. 완료 기준

- `.claude/skills/generate-quiz/`에 SKILL.md와 references/quiz-rules.md가 있다
- **기존 퀴즈 8편에 `npm run check:quiz`를 돌려 에러 0.** 이미 리뷰를 거친 글들이라 에러가 나오면 스크립트 기준이 과한 것이다. 경고는 나와도 된다
- 일부러 깨뜨린 픽스처로 주요 검사 항목(정답 노출, YAML 깨짐, 한/영 불일치)이 실제로 잡히는지 확인
- `npm run check` (tsc) 통과
- CLAUDE.md 퀴즈 절이 포인터로 줄었고, 옮긴 규칙에 유실이 없다

## 11. 선행 조건

`node_modules`에 `remark-math`와 `rehype-katex`가 없어 현재 `npm run check`가 실패한다. 구현 전에 `npm install`이 필요하다.
