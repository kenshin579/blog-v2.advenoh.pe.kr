## 1. 배경과 목적

시스템 디자인을 스터디하면서 정리한 내용을 블로그 시리즈로 남긴다. 첫 주제는 URL 단축기(URL Shortener)다.

목적은 URL 단축기 자체의 지식보다 **"모르는 시스템을 어떤 순서로 설계해 나가는가"**라는 방법론을 익히는 데 있다. 따라서 글은 시스템 디자인 인터뷰에서 쓰이는 4단계 프레임워크를 그대로 따라가고, 이 틀을 시리즈의 다음 주제에도 재사용한다.

주제는 ByteByteGo 챕터 목록에 한정하지 않는다. 참고자료가 있는 주제부터 순서 없이 다룬다.

### 검토했으나 채택하지 않은 것

- **Go 구현 포함**: 초기에 검토했으나, 설계를 충분히 이해하기 전에 구현 스택(SQLite/Redis/벤치마크 구성)을 결정하는 것은 순서가 거꾸로라고 판단해 보류. 구현편은 이 글을 쓴 뒤 **별도 작업**으로 다시 논의한다.
- **주제별 시리즈 분리**: 주제마다 별도 `series`를 두는 방식 대신 통합 번호를 선택했다. URL 단축기 구현편을 쓰면 2편, 다음 주제가 3편이 된다.

### 1. 개요

- 시리즈 소개와 이 글에서 다룰 범위
- 시스템 디자인 4단계 프레임워크가 무엇인지 짧게
- 썸네일 이미지 삽입

### 2. 1단계: 요구사항 명확화

- **2.1 기능 요구사항** — 긴 URL을 짧은 URL로 변환, 짧은 URL 접근 시 원본으로 리다이렉트. 커스텀 별칭과 만료는 이 글의 범위 밖임을 명시
- **2.2 비기능 요구사항** — 고가용성, 낮은 지연, 추측 불가능한 짧은 URL
- **2.3 개략적 규모 추정** — 아래 가정에서 역산

  | 항목 | 값 |
  |---|---|
  | 쓰기 | 일 1억 건 → 약 1,160 QPS |
  | 읽기 | 쓰기의 10배 → 약 11,600 QPS |
  | 10년 누적 | 3,650억 건 |
  | 레코드 평균 크기 | 100바이트 → 약 36.5TB |

- **2.4 짧은 URL 길이 역산** — `62^n ≥ 3,650억`을 만족하는 최소 n을 구한다. `62^6 ≈ 568억`으로 부족하고 `62^7 ≈ 3.5조`면 충분하므로 **7자**. 숫자를 왜 이렇게 잡는지, 추정이 설계에 어떤 제약을 만드는지 설명한다

### 3. 2단계: 개략적 설계

- **3.1 API 설계** — 단축 엔드포인트(POST)와 리다이렉트 엔드포인트(GET) 두 개. 요청/응답 형태
- **3.2 리다이렉트 동작과 301 vs 302** — 이 글의 **첫 번째 트레이드오프**이자 깊이를 몰아줄 지점 ①
  - 301(영구): 브라우저가 캐싱해 두 번째 요청부터 서버를 거치지 않음 → 서버 부하 감소, 그러나 클릭 분석 불가
  - 302(임시): 매번 서버를 경유 → 분석 가능, 부하 증가
  - 무엇을 우선하느냐에 따라 갈린다는 점을 명확히
- **3.3 데이터 모델** — 개념적으로는 해시 테이블(짧은 URL → 긴 URL). 실제로는 관계형 테이블 `(id, shortURL, longURL)`
- **3.4 상위 아키텍처** — 클라이언트 → 로드밸런서 → 애플리케이션 서버 → 캐시/DB

### 4. 3단계: 상세 설계

- **4.1 접근 ①: 해시 함수** — CRC32, MD5, SHA-1 등의 결과에서 앞 7자를 잘라 쓰는 방식. 단순하지만 충돌이 발생
- **4.2 충돌 처리** — 깊이를 몰아줄 지점 ②
  - 재시도 방식: 충돌 시 사전 정의된 문자열을 붙여 다시 해싱
  - 문제는 **쓰기마다 "이 키가 이미 있는가" DB 조회가 필요**하다는 것
  - Bloom filter로 이 조회를 대부분 건너뛸 수 있음을 3~4문장으로 소개. "없다"는 답은 확실하므로 DB를 보지 않아도 된다는 성질만 짚고, 비트 배열·해시 개수·오탐률 같은 자료구조 내부는 다루지 않는다
  - 규모가 작으면 unique 인덱스 + 위반 시 재시도로 충분하다는 점도 함께
- **4.3 접근 ②: 유일 ID + Base62 변환** — 유일한 ID를 62진법으로 변환. ID가 유일하므로 결과도 유일 → **충돌 자체가 발생하지 않음**
- **4.4 유일 ID 생성기가 어려운 이유** — 깊이를 몰아줄 지점 ③
  - DB auto increment는 단일 DB 전제. 분산 환경에서 깨짐
  - 대안: Snowflake, Redis INCR, 키를 미리 만들어 두는 키 생성 서비스(KGS)
  - 각 방식의 트레이드오프(단일 장애점, 순차성 노출, 운영 복잡도)
- **4.5 두 접근 비교** — 표로 정리. **접근 ②는 충돌 처리와 Bloom filter가 아예 불필요**하다는 점을 표에서 못 박는다
- **4.6 읽기 편중과 캐시** — 읽기가 쓰기의 10배이므로 캐시가 핵심. cache-aside 흐름, 캐시 미스 시 동작
- **4.7 전체 흐름 정리** — 단축 흐름을 다이어그램으로 정리한다. 리다이렉트 흐름은 4.6의 캐시 다이어그램이 이미 담고 있으므로 다시 그리지 않고 참조만 한다

### 5. 4단계: 마무리 — 더 고민할 것들

**린 방침에 따라 각 항목 1~2줄, 목록 수준으로만 다룬다.** 여기서 깊게 들어가면 3~4장의 핵심 트레이드오프가 묻힌다.

- DB 샤딩과 복제
- 만료(TTL)와 정리
- 커스텀 별칭
- rate limiting과 악성 URL 차단
- 클릭 분석 파이프라인
- 멀티 리전과 CDN

### 표 3개

1. **규모 추정 결과** (2.3) — 쓰기 QPS / 읽기 QPS / 10년 저장량 / 짧은 URL 길이
